# AGENTS.md

Python CLI/library for time-optimal trajectories of a LEGO/FLL differential-drive robot (CasADi + IPOPT), plus robot-side Pybricks code. The library lives in the `overboard/` package; there is no install metadata (no `pyproject.toml`), so run every command as `python -m overboard.…` from the repo root.

This file is the index: the rules, the entry points, and where the rest lives. Detail - measurements, thresholds, feature tours, the reasons a rule exists - is in `docs/AGENT_OPS.md`, one section per topic; read only the section a task needs.

**Where the code is.** Only `benchmark.py`, `run_tests.py` and `testcache.py` sit at the root.

## Read first

- `docs/PROJECT_GOAL.md` is what the project claims and why: the setting, the three classes of failure, the objective order (**spread first, then time, then pose error**), and the secondary goal that a new robot goes from uncalibrated to a deployed, validated path unaided. Read it before deciding what a change is *for*; read `KNOWN_ISSUES.md` for what is currently in the way.
- `KNOWN_ISSUES.md` is the source of truth for risky paths. Open: KI-020 (hardware calibration and digital-twin validation). Mitigated: KI-032 (the test cache) and KI-054 (the envelope gate's absolute limit is a duration gate; `--field-clearance` prices it against the field where geometry exists). Deleted: KI-004 (the Multi-Verse seed provider; archived in git tag `archive/legacy-2026-10`). Everything else in KI-001..KI-053 is fixed. Cite KI IDs; do not silently "fix" an open one unless asked. Read the **Quick triage** table at the top - one line per entry - and open an entry only when you are working on it. The entries below it are short records grouped by status (**Open**, **Mitigated**, **Archived**, **Fixed**): what was wrong, what changed, which files carry the fix. The long narrative each entry used to carry is in the git history (`git log -p KNOWN_ISSUES.md`).
- `--validate` is a hard gate, and the validation model is not yet a full digital twin (KI-020).
- `docs/HEURISTICS_AND_VERIFICATION.md` before changing the initial-guess seeds, the timing models, the candidate set, the selection rule or the validation thresholds. Start at "Findings at a glance" and its table of contents, not page one. Its two research parts have their own files: `docs/STRATEGY_LEDGER.md` (the strategies that failed, with the measurement that retired each) and `docs/RESEARCH_AGENDA.md` (the open questions) - do not re-litigate a failed strategy without new evidence. Same for `docs/research/RQ-A_tracking_error.md` before changing the optimizer's kinematics, the reference interpolation, the tracking gate or its 5 mm threshold - its "short answer" is the part you need.
- The Multi-Verse pipeline has been removed (archived in git tag `archive/legacy-2026-10`). The 3-Pillar unified planner is the **only** planner: the stock candidate set and the other engines are retired, and their flags are removed and rejected. Where a doc and the tree disagree, the source is the authority.

## Commands

- Install the core path: `pip install -r requirements.txt` (solver and studio). `--validate` and `--push-hub` also need `pip install -r requirements-optional.txt` (jax, immrax, pybricksdev). `install.bat` / `sh install.sh` builds `.venv` with both and runs the check; `start_studio.bat` / `sh start_studio.sh` start the studio with it. The `.bat` files must keep CRLF line endings (`cmd.exe` cannot find a batch label in an LF file) and the `.sh` files must stay LF. §Install.
- `python -m overboard.main --doctor` reports the Python version, every package, the example files, the output directory and the ports, with the install command for anything missing. Run it first when something does not work.
- Quick, predictable run:
  `python -m overboard.main -w examples/example_straight.json -o output.traj`
- The 3-Pillar Unified Trajectory Engine is the **only planner**: it owns the candidate set and the seeds, and the CasADi/IPOPT optimizer is the backend it drives. `--no-unified` and `--simple` are **removed and rejected** (`tests/test_cli_ux.TestDeprecatedCliFlags` pins it). §Solve options.
- The candidate set is the planner's: three frontier candidates (`sprint`/`sweeper`/`exploratory`, per-segment, discretization metric) followed by the Q17 tail (`frontier_sprint_mirror`, `frontier_spline`, `frontier_reverse`; mirrored bow, bezier geometry, reverse-seeded segments). `--candidates N` (default 2) slices that list positionally. **The tail is opt-in and inert at the default** (Q17, 2026-10-26: it solves back to one path and bought zero gate coverage on the 32-mission suite, 6/32 in both arms), so `--candidates 3` is the triad and `--candidates 6` is the gate-coverage mode - extra tickets, not a wider basin set. The per-segment timing model is the only model, held to the wheel-jerk discipline (KI-022, KI-024). A mission's scoring budgets are measured, never guessed (the M1 rule, `docs/EXAMPLES.md`): re-measure them when the solved candidate set changes, because the duration score only means something against the plan the current set produces. The five seeds (`rolling`, `frontier_sprint`, `frontier_sweeper`, `frontier_exploratory`, `baseline`) are still declared in `overboard/core/optimizer.py` and nothing solves them (KI-048 removed). **Do not force a mode silently.**
- A waypoint is a timing boundary only when the robot stops there AND the heading is pinned; elsewhere the pieces stay linked and the per-segment model requires the wheel acceleration - and so the wheel force - to be continuous through the point (KI-024). `TrajectoryOptimizer.merge_conditions(waypoints, stop_waypoint_indices=None)` is the one place that rule lives.
- **There is no rescue round.** The CLI solves the planner's candidate set and stops there (KI-048 removed): over the 32-mission suite it rescued 0 of the 22 failing missions, and 95 of its 97 checked failures were the envelope, which a seed cannot move. The five stock seeds are still declared in `overboard/core/optimizer.py`; nothing solves them.
- The opt-in solve paths, all off by default: `--fast-polish` (200-iteration warm budget, cold finish, fallback to the unbudgeted pass, KI-047), `--force-weight` (prices wheel-force utilisation instead of only bounding it) and `--polish` (the post-solve gradient polish: the reachability rollout is differentiated and the plan is re-solved with the samples the gradient points at weighted; it needs JAX). `--sweep`, `--uniform-dt`, `--simple`, `--no-unified`, `--surrogate-polish`, `--pyramid`, `--pyramid-candidates`, `--h-adaptive`, `--self-consistent` and `--no-self-consistent` are **removed and rejected** as unknown options (`tests/test_cli_ux.TestDeprecatedCliFlags` pins it). The 3-Pillar Unified Trajectory Engine is the only planner. The CLI has no wrapper for the browser studio (`--live`, `--show-convergence`, `--convergence-mode` are gone; `--gui` is the one way in). Do not enable an opt-in path silently. §Solve options.
- The optimizer also takes three parameters the command line does not expose: `cost_metric` (`"jerk"` or `"discretization"`), `epigraph_constraints` and `sample_weights`. `TrajectoryOptimizer.solve` reads them. §Solve options.
- `--preset fast|safe` fills in only the options the user did not set: fast = 8 samples per segment, 1 candidate without validation, safe = 3 candidates with `--validate`, `--propagation tick` and a controller export (the open-loop tube grows with distance). Explicit flags always win.
- `--validate` gates every output and the exit code, and requires JAX/Immrax and a scoring timing budget (`target_time_s`/`max_time_s` from the mission's `scoring` section or `--target-time`/`--max-time`; unvalidated solves do not need one). It solves the candidate set (parallel when validating), validates each, and scores each with the **decision score** (`score_version: 1`, capped 0-100, NOT a probability of hardware success): a weighted average of physical/accuracy/quality/duration in the named profiles `precision` 20/35/35/10, `balanced` 25/25/25/25 (default), `speed` 20/20/20/40 (`--scoring-profile`), capped at the score of a category the candidate failed. An ordinary pass is eligible; a failed candidate only under an explicit `--accept-score N` (its score at or above N); a structural failure (non-convergence, crashed/incomplete validator, diverged or unbounded tube, missed final waypoint, nominal body inside a mission model) is never eligible, exported or pushed. The highest score selects (ties: pass before accepted, then accuracy, physical, duration, index). The 5-part path fitness score (stop spread, slip risk, RMS wheel force, tracking error, run time) is reported for every candidate as a legacy diagnostic, not the selection score. Without `--validate`, only the first candidate is solved. **If validation fails, no `.traj`, controller, Python file or `_stats.json` is written** - unless `--best-effort` or `--accept-score` applies. `--best-effort` exports the best converged candidate when the only failure is an accuracy excess (envelope or tracking), marks the `.traj` root and `_stats.json` with `validation: {passed: false, best_effort: true, hub_approved: false, ...}`, prints the excess, and is never approved for the hub. An accepted failure records `passed: false, accepted: true, hub_approved: true` and may drive the hub. A force, slip, integration or divergence failure is scorable/accepted only through `--accept-score`; a structural failure always writes nothing. `--envelope-limit METRES` (0.001-0.05, default 0.02) is the run-wide envelope budget; a waypoint's `error_threshold` still wins, the cap is where the propagation cuts the tube off (KI-049), and the limit in force is recorded in the report (`envelope_limit_m`) and in the file. The limit is absolute by default, so a long path can fail for being long (KI-054); `--envelope-limit-per-metre M/M` (default 0, max 0.05) adds that much allowance per metre travelled. `--field-clearance SEASON` (opt-in, needs `--validate`) makes the gate field-aware twice over, from one field model. The robot is its **heading-aware body box** - the rectangle from `back_bumper_m` behind to `front_bumper_m` ahead, `width_m` wide, at the sample's heading (its circumscribed disc is `chassis_radius_m()`). The accuracy limit becomes the space around that box per sample (clamped 0.005-0.05 m; a waypoint's `error_threshold` still wins locally, a sample the field cannot measure falls back to the flat limit, and the field's ~100 mm placement uncertainty is recorded with the limit, never subtracted), and the clearance to the **mission models** is its own physical failure class - `tube_radius / max(raw_clearance, 1e-6)` above 1 fails like force or slip (the clamp can never mask a penetration), so `--best-effort` never exports it and only `--accept-score` can. The mat edge is a game-rule boundary, not a crash: the chassis may legally overhang it (it still shapes the accuracy limit), and the nominal box **inside a mission model** is a structural failure - unscored, never eligible, never exported even with `--accept-score`. §Validation.
- `--propagation [plant|tick]` picks the reachability model the envelope gate uses (KI-049, KI-050). "plant", the default, propagates the plant open-loop with the controller evaluated outside the tube; "tick" embeds one closed-loop tick, so the tube contracts like the robot's - it needs a Jacobian inclusion and costs 2-3x (`jac`) to 7-10x (`mjac`) the validation time. `research/harness.py` takes the same flag. **An envelope is never read without its model**: every candidate carries `propagation` and `inclusion`. §Validation.
- `--validate --export-format controller` writes `<output>_controller.json`; `python` writes `<output>.py`; `python-compact` writes the packed module for `ramsete_compact.py` / `ramsete_compact_events.py`; `--benchmark` writes `<output>_stats.json` after the export gate.
- The hub path is `--push-hub` (writes `pybricks_code/hub_mission.py`, pushes `hub_runner.py`; `--hub-conn ble|usb`, `--hub-name`, `--hub-log`), `python -m overboard.deploy.hub_deploy <script.py> [--out session.csv]` for any script, and `python -m overboard.sysid.collect --conn ble` for the one-command SysId loop. **Every trajectory push enforces approval**: `--push-hub` requires `--validate` and an approved run, and `hub_deploy.push_trajectory` / `--trajectory` re-reads the `.traj` and refuses unless `validation.hub_approved` is true with `score_version: 1` and `trajectory_sha256` still matching the file - before it writes the mission, syncs the robot config or connects. `overboard/deploy/hub_deploy.py` owns `trajectory_sha256` / `check_trajectory_approval` so writer and pusher cannot drift; a raw script deploy is unrestricted. Bluetooth discovery goes through `overboard/deploy/hub_ble.py` (KI-033); `python -m overboard.deploy.hub_deploy --list-hubs` is the device picker. It needs `pybricksdev`; a plain solve never imports it. §Export.
- Browser studio: `python -m overboard.main --gui` (port 8000 on `127.0.0.1`, `--gui-port`, next free port if busy). It serves `overboard/viz/studio.html` from `overboard/gui_server.py`, runs the CLI in a subprocess and **never bypasses the export gate**; it leaves the backend at the CLI default and runs one solve at a time (`GET /api/jobs/current` attaches). Its push button and `pushToHub` allow what the server allows - a validated pass, or a failed plan accepted by its score and marked hub-ready - and the push itself is gated server-side on the trajectory's approval (`hub_approved`, `score_version: 1`, a `trajectory_sha256` that still matches the exported file - the same rule the CLI enforces). The Run tab's **Scan for hubs** (`POST /api/hubs`) lists the devices Bluetooth can see the way `--list-hubs` does, and fills the hub-name field; it is refused while a job runs, because a push holds the hub's single connection. A compare run writes every solved candidate with `--candidates-out`, so the studio draws the frontier paths together; the chips pick one, and the chosen one is exported with `--pick-candidate N` - refused unless that candidate passed every gate or is eligible under an active `--accept-score`, so the rule is overridden by a human who saw the numbers, never suspended. `docs/STUDIO_UI_INVENTORY.md` + `tests/test_studio_inventory.py` must stay in step with the markup. The studio side of the score contract is built: `gui_server.py` and `overboard/viz/*` read the mission `scoring` schema and forward the scoring flags only with `--validate`; they forward `--field-clearance` the same way and show the per-sample field limit next to the accuracy limit with its ~100 mm placement uncertainty, and the clearance util / penetration under the Physical score category. §The browser studio.
- Desktop build: `pyinstaller --noconfirm overboard.spec` writes a **one-folder** app with the studio, the solver and JAX (never one-file: it unpacks tens of thousands of files on every launch); `installer.iss` wraps it for Windows, and `.github/workflows/desktop.yml` builds all three OSes on a `v*` tag and smoke-tests solve + `--doctor` (+ `--validate` on Linux). The entry is `overboard_desktop.py`, which dispatches `--run-cli` / `--run-hub`; the studio uses those instead of `-m` when `sys.frozen`, because `sys.executable` is then the app itself. Writable state comes from `overboard/paths.py`: `ASSET_ROOT` is the read-only bundle, `STATE_ROOT` the user folder (`OVERBOARD_HOME` overrides it), and `pybricks_code/` is seeded there on first run because the mission and the robot config are written. The app explains itself offline: `overboard/viz/help.html` (served as `/help.html`, linked from the topbar, so it is not a `<button>` and stays out of the studio inventory counts) plus a copy of `docs/` and the root `.md` files in the state folder. §Desktop build.
- With `--validate`, `overboard/main.py` prints one machine-readable line per run: `##OVERBOARD-VALIDATION## {json}` with the per-candidate and per-segment envelope, limit, drift, reasons, the accuracy weight of each candidate and its score vector (`duration_s`, `envelope_cm`, `tracking_cm`, `max_excess_cm`, `peak_jerk_m_s3`, `fitness_s` and its parts), plus the decision score (`score`, `score_version`, `categories`, `ratios`, `eligibility`, `accepted`, `structural_failure`) and run-level `profile`, `accept_score`, `accepted`, `hub_approved`, so the selection rule can be re-run offline. **Keep the JSON valid** (`Infinity` breaks `JSON.parse`); nothing is written to disk on a failed validation, so the report goes to stdout only. A short plain-language verdict block (`In short: ...` lines: score + profile + the "decision units, not a probability of hardware success" caption, the verdict in plain words, one next step) prints **above** the machine line and never below it - `output.split(VALIDATION_MARKER)[1]` must stay pure JSON - and it appears only with `--validate`.
- `docs/CALIBRATION_PROCEDURE.md` is the human procedure; `docs/CALIBRATION_STUDIO_PLAN.md`, `docs/STUDIO_HUB_PLAN.md` and `docs/STUDIO_3D_SIMULATOR_PLAN.md` are the designs for the studio's sysid loop, its push-to-hub and the 3D simulator. Calibration-critical tests run three times with the step order reversed on every other repeat and a 95 % t-interval per parameter; the drift is a **slope, not a subtraction**; the motor's stall torque and no-load speed are measured and written into the robot config, so every tool plans against the same motor (KI-010). The fit also lands the sheet's weigh-in mass and the inertia derived from the turn steps, with measured ranges, into the robot config; both are validated against the digital twin only (KI-020 open). §Calibration.
- Tests: `python run_tests.py` (the runner prints the count; do not quote one in docs). Single test: `python -m unittest tests.test_optimizer.TestTrajectoryOptimizer.test_init -v`
- Agent loop: `python agent_report.py tests|bench|solve ...` runs the command and prints only the summary, the validation JSON and the final lines. Project commands live in `.opencode/commands/` (`/check`, `/solve`, `/bench`, `/triage`, `/studio`, `/reviewer`); the read-only reviewer is `.opencode/agents/reviewer.md`, and the project guardrails are in `.opencode/opencode.json`.
- Cross-check: `python research/crosscheck/compare_step.py` against an independent rigid-body simulator (WSL2; `research/crosscheck/README.md`). Measurement code, changes nothing in the planner.
- Stress run: `python research/suite.py --count N --seed S --out DIR`, then `python research/harness.py --missions DIR --out FILE`, read back with `python research/analyze.py errors|robots FILE`; pin the tree with `OVERBOARD_TREE` while editing. Benchmarks: `python benchmark.py --mode pipeline|cli|random|solver` (default config `examples/fll_choreo.json`) - all four work (KI-015), and `--mode solver` is the reference table for a solver change. §Research.
- `--plot`, `--animate` and `--gui` are blocking; keep automated runs headless.

## Test quirks (verified)

- `run_tests.py` imports the JAX test modules in a `try`; without JAX it prints a warning and skips them. With JAX the full suite runs with 0 failures and 0 skipped; the three `TestRoboVibeConverter` cases skip only when PyYAML is missing (they pass when it is installed). A stale import in that `try` block silently skips the whole JAX suite, so `tests/test_suite_registry.py` is the guard against it.
- The runner holds an **explicit list of the test classes it runs** (`test_classes()`), so a class that is not in the list never runs. `tests/test_suite_registry.py` checks that every test class in `tests/` is listed.
- The suite keeps a **test cache** (`testcache.py`, `.test_cache.json`, gitignored). A test that PASSED is skipped when nothing it reads has changed; a failure always runs again, and a test that wrote a file inside the repository is never skipped. The cache never decides that a test passed - it only says a test does not have to run again. `--cache-status`, `--no-cache`, `--clear-cache`, `--durations 20`. Measured 292 s cold, 5 s warm (KI-032). §Research.
- The old `test_stomp_variants.py` and `test_teb_topologies.py` modules are deleted. Do not reintroduce tests for removed `MultiVerseRefiner` / `LocalSegmentOptimizer` classes.
- JAX/refinement modules: `python -m unittest tests.test_jax_ramsete tests.test_polish tests.test_envelope_soundness`
- `tests/test_cli_ux.py` and `tests/test_gui_server.py` cover the CLI surface and the studio server (a real server on an ephemeral port and one real solve). `tests/test_studio_honesty.py` pins what the studio owes the operator (the push needs a validated trajectory, a failed solve leaves no path on the field, an error carries no internal path, `hidden` actually hides - KI-030).

## Architecture and contracts

- `overboard/main.py` is the only CLI entry point. It defaults to `TrajectoryOptimizer` (CasADi/IPOPT). The old Multi-Verse pipeline has been removed. §Planner internals.
- `TrajectoryOptimizer.solve` **splits the path** at the waypoints where the robot stops AND the heading is pinned, solving each piece as its own NLP and keeping the cheapest seed. Opt-out (`split_at_boundaries=False`). A failed solve returns `converged: false` with `error` and `error_kind` (`max_iter` / `infeasible` / `numeric` / `unknown`, from `overboard.core.optimizer.classify_solver_error`; the stitched split path propagates it) - the label describes the failure and never changes eligibility (Q20).
- The **sample count follows the path**: `get_segment_sample_counts` splits the budget in proportion to arc length (at least three samples each, and a segment that turns more than 20° gets the full per-segment count), and `waypoint_sample_indices` / `stats["segment_samples"]` map a sample back to its waypoint. Seeds and the objective follow that layout, so a measurement must say which layout it was taken on.
- The position rule is unconditional: it integrates with four-node Gauss-Legendre along the integrated heading, so the samples lie on the path the plan's own (v, omega) profile traces (KI-026, KI-051, KI-052). The trapezoidal branch and its switch were removed. §Planner internals.
- The reference interpolates heading, speed, turn rate and Ramsete gain as independent lines, but they are coupled: the turn rate must be the derivative of the interpolated heading and the gain `sqrt(w^2 + b*v^2)` of the interpolated values. All four controller modules and `overboard/verification/immrax_validator.py` do that, and the heading difference is taken the short way, as the firmware does (KI-027).
- The validator models the controller that **runs** (synced 20 ms heartbeat, floats to `drive()`, no rounding - KI-027, KI-028), and **there is one implementation in the firmware**: `ramsete.py` holds the odometry, the Ramsete maths and the loop; `ramsete_fast.py` delegates to it and `ramsete_compact.py` delegates to `ramsete_compact_events.py` with events off. `tests/test_firmware_events.py::TestFirmwareParity` pins it. The firmware `KinematicLimiter` uses the per-wheel traction limit with lateral weight transfer and the robot's own fallback numbers, and applies no backlash: backlash is a position uncertainty in the reachable set (KI-025), never a velocity offset. §Planner internals.
- The validator has two propagations (`PROPAGATION`): "plant" is the default, "tick" is opt-in. The tick map needs the mixed Jacobian inclusion and the pose must be read by indexing, never unpacked (`x, y, theta = pose` is `unstack`, which has no inclusion rule). §Validation.
- `overboard/models/robot_model.py` parses the canonical `{"robot": {...}}`, legacy Choreo `{"config": {k: {"val": ...}}}` and flat dicts identically, including `robot.uncertainties`; `JAXRobotConfig` delegates to `RobotConfig` (KI-008).
- The optimizer and validator share one per-wheel force model (`wheel_normal_forces`, in `overboard/models/drivetrain_physics.py`): lateral weight transfer only, no front/rear split; Immrax uses the same ranges (KI-009, KI-010).
- Heavy imports are lazy: a plain solve must not import JAX, Immrax, the archived Multi-Verse code or the plotters. `overboard.main.ImmraxValidator` and `overboard.main.JAXRobotConfig` stay at module level (`None` until `_ensure_jax_classes`) so tests can patch them.
- Waypoints are dicts or `[x,y,heading]`, optional `stop`, `event`, `error_threshold`, `precision_mode`; a mission may wrap them as `{"waypoints": [...], "scoring": {target_time_s, max_time_s, jerk_target_m_s3, jerk_max_m_s3}}` - plain lists stay valid. An event on the final waypoint lands on the last sample and fires after the loop, once the drivebase has stopped (KI-012).
- Output is Choreo v3 (`trajectory.samples`). Keep the sample schema (`t,x,y,heading,vl,vr,omega`, forces, optional `event` / `reachability_envelope`) stable: validator, exporter, plotters and the Pybricks runtime consume it. The `.traj` root and `_stats.json` always carry `validation`: a pass records `passed: true` and its limits, an accepted failure `passed: false, accepted: true, hub_approved: true`, a best-effort file `passed: false, best_effort: true, hub_approved: false`, and a run without `--validate` `{status: "unvalidated", passed: false}`. Every record also carries `score`, `score_version: 1`, `profile`, `weights`, `categories`, the scoring timing and `trajectory_sha256` (canonical `{"config": ..., "samples": ...}` SHA-256, computed by `overboard/deploy/hub_deploy.py`). A file without one must not be read as approved.
- `pybricks_code/` is firmware, not CPython (`pybricks.*`, `umath`); do not run it on the host. `complex_mission.py` is generated by `--export-format python` - regenerate, do not hand-edit (KI-018); it stays because `sysid_digital_twin.py` replays it. The other generated demo (`complete_mission.py`) and the demo missions are in `pybricks_code/archive/`. §Planner internals.
- MicroPython cannot concatenate two f-strings: build output with one `%` format or one f-string per statement. `tests/test_hub_deploy.py::TestFirmwareCompiles` compiles every file in `pybricks_code/` with mpy-cross.
- The hub-to-host contract is the session format: `TEST_START <name>`, `META,key,value`, a `DATA` block with a `t_ms,...` header, `TEST_END,<n>`; a test reports `POSE,x_m,y_m,heading_deg` and `EVENT,name`, and a pose takes the run id of the test that was open. Never break those line formats; the planner's heading is counter-clockwise positive while `drivebase.angle()` is clockwise positive.
- `hub_runner.py` is the only hub entry point for a pushed trajectory: it imports the generated `hub_mission.py` (gitignored) and the hardware from `robot_config.py`, and returns the final odometry pose. Event actions live in the runner's `MISSION_EVENTS`; `robot_config.py` stays hardware-only.
- Root-level `.traj`, `*_controller.json`, `*_stats.json` and `test_output*` are generated artifacts, not source. `overboard/sysid/fit.py` is host-side; it never runs on the Hub.
