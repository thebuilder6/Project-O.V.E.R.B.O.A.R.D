# AGENTS.md

Python CLI/library for time-optimal trajectories of a LEGO/FLL differential-drive robot (CasADi + IPOPT), plus robot-side Pybricks code. Flat modules, no packaging: run every command from the repo root.

## Read first
`KNOWN_ISSUES.md` is the source of truth for risky paths. Fixed in the codebase: KI-001 through KI-003, KI-005 through KI-019, KI-021 through KI-031, KI-033 through KI-044, KI-045, KI-046, and KI-047 through KI-050. Mitigated: KI-032 (the test cache). Open: KI-004 (seed provider), KI-020 (hardware calibration & digital twin validation). Cite KI IDs; do not silently "fix" these unless asked.

The docs describe the current tree, but the source is still the authority. In particular, the Multi-Verse pipeline is repaired (its refined guess now wins the probe) and re-envisioned as a **seed provider**: `main.py --refine` puts its refined trajectory into the candidate set. Measured on 30 missions, the refined seed is *not* better than the stock seeds and rescues nothing - it is a cheaper way to reach the stock set's speed (the complex mission: 4.936 s against the default set's 6.068 s), so it stays opt-in (KI-004). `--validate` is a hard gate, and the validation model is not yet a full digital twin (KI-020).

## Commands
- Install the core path: `pip install -r requirements.txt` (solver and studio). `--validate`, `--multiverse` and `--push-hub` also need `pip install -r requirements-optional.txt` (jax, jaxopt, immrax, pybricksdev; verified with JAX 0.6.2 and pybricksdev 2.3.2; a fresh install brings JAX 0.12.0 and Immrax 0.3.8, which need numpy 2.2, so requirements.txt asks for numpy below 3.0 and not below 2.0).
- The one-click path for a new user: `install.bat` (Windows) or `sh install.sh` (macOS/Linux) creates `.venv`, installs the core and the optional packages and runs the check. `start_studio.bat` / `sh start_studio.sh` start the studio with that `.venv`, and install it first when it is not there. `main.py` reports the install command instead of an ImportError when the core packages are missing, so `--doctor` works on a clean machine. The `.bat` files must keep CRLF line endings: `cmd.exe` cannot find a batch label in a file with LF endings, and `install.bat` calls a subroutine. `.gitattributes` keeps them out of the line-ending conversion so the CRLF survives into a ZIP download; the `.sh` files must stay LF.
- `python main.py --doctor` reports the Python version, every package, the example files, the output directory and the ports, with the install command for anything missing. It is the first thing to run when something does not work.
- Quick, predictable run:
  `python main.py -w examples/example_straight.json -o output.traj`
- The simple CasADi solver is the default; `--multiverse` opts into the experimental pipeline and `--simple` is a deprecated alias. `--refine` (simple solver only, needs JAX) adds the **Multi-Verse pipeline's refined trajectory** to the candidate set: the pipeline is used as a seed provider, not as a second solver. Its phases 1-4 (Reeds-Shepp bootstrap, kinematic profile, critic, segment-preserving refinement) cost about 2 s and hand the solver a path through every waypoint with a per-segment interval; the solver does the magnitudes, so the refined trajectory is only used with the per-segment timing model. On `examples/example_complex_mission.json` it gives 4.936 s where the default two-candidate set gives 6.068 s and the full ten-candidate stock set gives 4.877 s - so it is cheaper, not better, and it rescues no mission (KI-004). Off by default: it needs JAX and costs a refinement and a solve per candidate. Do not use `--workers`/`--no-parallel` as a quality claim.
- The default candidate set mixes the two timing modes: candidate 1 is equal-duration baseline, candidate 2 is per-segment baseline, then remaining seeds alternate. `--uniform-dt` / `--per-segment-dt` force one mode. The equal-duration mode shares one `dt` across all segments, which because every segment has the same sample count also forces every segment to take the SAME time; on a path with unequal segment lengths that is a large artificial penalty, so the per-segment mode is the general model (setting every `dt_i` equal recovers the equal-duration solution). Both modes are held to the same wheel-jerk discipline, so `--accuracy-weight` means the same thing in either (KI-022). A waypoint is a legitimate timing boundary only when the robot stops there AND the heading is pinned: everywhere else the pieces must stay linked, and the per-segment model now requires the wheel acceleration — and so the wheel force — to be continuous through the point (KI-024). The complex mission selects the equal-duration candidate at 6.068 s / 1.22 cm; the per-segment candidate is faster there (4.650 s) but fails the gates at `accuracy_weight=0`. Per-segment wins on uneven segments at a small weight (e.g. `-a 0.005`: 2.784 s / 0.32 cm / 0.36 cm against the equal-duration 4.456 s); at `-a 0` it is 2.710 s but fails the Immrax and CPU gates, so the loop falls back to the equal-duration candidate. The CPU audit runs per candidate, so a partial pass cannot block a later fully passing candidate. Do not force a mode silently. **When a run produces nothing usable - no candidate passes the gates, or (without validation) none converged - the CLI tries the other seeds as a rescue before giving up** (KI-048): the two default candidates share one seed, so without the rescue a path that beats the baseline seed ends with no trajectory at all. The rescue uses the per-segment model on a validated run (that is where the measured rescues came from) and the same model on an unvalidated one; a rescue candidate is only selected when the candidate set itself produced nothing that passed. It costs nothing when the plan works, and one parallel round of solves when it does not.
- `--fast-polish` uses the fast solve path: the warm-start IPOPT pass gets an iteration budget (200) and, if it runs out, the mission is solved cold from the original guess (KI-047). A mission that converges inside the budget returns a bit-identical trajectory. Measured on the 10-waypoint complex mission (2026-10-20, the working tree): the plain warm pass is 1557 iterations and 6.068 s in 35 s, `--fast-polish` is 200 + 154 = 354 iterations and 6.124 s in 7 s - 4.4x fewer iterations and 5x less wall time for a trajectory 0.9% slower, because the cold finish converges to a different optimum. A mission where the cold finish fails falls back to the unbudgeted pass, so nothing that solves today stops solving. Off by default; do not enable it silently.
- The candidates are independent, so `--validate` with `--candidates N` solves them in worker processes (`--workers`, `--no-parallel` keeps them in this process) and then scores them one by one here, where the JAX validator is warm. The trajectories are identical to the sequential run. `--show-convergence` stays sequential because it needs the solver in this process. A patched or injected optimizer also stays sequential: a worker cannot import it.
- `--sweep` (simple solver only) adds the timing-mode x accuracy-weight grid (weights 0, 0.001, 0.002, 0.005, 0.01) to the candidate set, so ten candidates are solved and validated instead of two. It never removes the default candidates, so it can only add options. Measured: with the merge conditions in place (KI-024) the default two candidates already pick the per-segment candidate on `examples/example_mission_first4.json` (1.833 s, 0.27 cm) and on `examples/example_with_events.json` (4.416 s, 0.88 cm), so the sweep no longer changes those two; the complex mission is unchanged at 6.068 s. Off by default; it costs ten solves and ten validation passes.
- `--preset fast|balanced|safe` fills in options the user did not set: fast = 1 candidate without validation, balanced = the defaults, safe = 3 candidates, `--validate` and a controller export. Explicit flags always win.
- `--validate` gates every output and the exit code. It requires JAX/Immrax. With `--candidates N` (default 2, max 5), `main.py` solves N trajectories. With the simple solver they combine initial-guess seeds (`baseline`, `rolling`, `bow_left`, `bow_right`, `turn_first`) with timing mode (equal-duration baseline, per-segment baseline, then alternating) at the same base accuracy weight; the Multi-Verse path still uses accuracy weights `base, base+2.0, ...` because seed and timing plumbing are only in `TrajectoryOptimizer`. It validates each candidate and selects a passing one by smallest envelope (shortest breaks ties). Without `--validate`, only the first candidate (equal-duration baseline) is solved. If validation fails, no `.traj`, controller, Python file, or `_stats.json` is written.
- `--propagation [plant|tick]` chooses the reachability model the envelope gate uses (KI-049, KI-050). "plant" is the default: the plant is embedded and propagated, and the controller is evaluated *outside* the propagation, at the tube's midpoint, so the tube bounds an open-loop plant driven by a pre-recorded command. "tick" embeds one 20 ms tick of the closed loop (controller, pose estimate and delayed command inside the map) and propagates that, so the map's Jacobian carries the feedback term and the tube contracts the way the robot's does. It needs a Jacobian inclusion (the natural extension explodes) and costs 2-3x (`jac`) to 7-10x (`mjac`) the validation time. The propagation and the inclusion functions are in every candidate of the `##OVERBOARD-VALIDATION##` line, so an envelope is never read without the model that produced it. `research/harness.py` takes the same flag. Measured on the six example missions (`docs/measurements/2026-10-20-tick/`): the tick tube is uniformly tighter - 2.9x on the S-curve, 3.2x on the stops, 4.4x on the complex mission - and the tracking error is identical to the last digit, so **no verdict changes**: four missions pass and two fail under both, and the two that fail fail on the tracking gate, which is the discretisation mismatch, not the envelope. The default stays on "plant": the tick map's own gain is on the paths where the plant propagation *diverges* rather than merely widens (a calibrated robot: the S-curve's plant tube is cut off at the 50 mm guard, 53.6 mm against the tick map's 18.8 mm), and with the digital twin it is wider still (12.1 cm against 5.1 cm), which is the conservative direction and not a hazard.
- `--validate --export-format controller` writes `<output>_controller.json`; `--export-format python` writes `<output>.py` (legacy list format); `--export-format python-compact` writes a packed module for `ramsete_compact.py`/`ramsete_compact_events.py`; `--benchmark` writes `<output>_stats.json` after the export gate.
- `--push-hub` pushes the trajectory to a Pybricks hub and runs it there, without the Pybricks IDE. It writes the packed trajectory to `pybricks_code/hub_mission.py` and pushes `pybricks_code/hub_runner.py`; pybricksdev bundles the local imports, so `robot_config`, `ramsete_compact_events`, `ramsete` and `hub_mission` travel with it. `--hub-conn ble|usb` picks the transport (BLE needs no driver; USB needs a WinUSB driver on Windows), `--hub-name` picks the hub, `--hub-log` saves the hub console output. The runner prints the measured pose as `POSE,x_m,y_m,heading_deg` and every exported event as `EVENT,name`. It needs `pybricksdev`; a plain solve never imports it.
- The hub over Bluetooth is found by **probing what is nearby**, the way the Pybricks IDE finds it (`hub_ble.py`): Windows does not report the advertised Pybricks service UUID and the local name in the shape `pybricksdev`'s filter wants, so the advertisement alone does not identify a hub (KI-033). `python hub_deploy.py --list-hubs` is the IDE's device picker: it shows what the adapter can see and says which device is the hub. The CLI, `--push-hub`, `sysid_collect.py` and the studio's push all go through it.
- `python hub_deploy.py <script.py> [--conn ble|usb] [--name NAME] [--out session.csv]` pushes any script to a hub and saves its console output, without solving anything. Use it to run the hub menu (`pybricks_code/robot.py`) or the sysid logger (`pybricks_code/sysid_digital_twin.py`) and capture the session that `sysid_fit.py` reads. `--out` is written as the output arrives, so a dropped Bluetooth link costs the last test instead of the whole session. `--list-hubs` pushes nothing: it lists the Bluetooth devices around and says which one is the hub.
- `python sysid_collect.py --conn ble --profile examples/drivebase_profile.example.json` collects a SysId session from the hub and fits it in one command: it pushes `pybricks_code/sysid_digital_twin.py`, captures the session as it arrives, converts the hub's `POSE` lines to `poses.csv`, and writes `sysid_fit.json`. The operator still presses the hub button between tests. A dropped Bluetooth link does not lose the run: the session is written as it arrives, so what arrived is fitted. The poses are the hub's own odometry, so the distance scale, the heading scale and the brake slip carry no information and stay at their defaults; replace `poses.csv` with tape measurements and re-run `sysid_fit.py` to calibrate them. The actuator part of the fit (gain, time constant, delay, backlash) needs no measurement and is calibrated either way. `--profile` is optional: only the fit needs the wheel radius, so the collect works without it and the command then says what to do next. `--sheet <path>` writes the measurement sheet after the collect: the CSV the fitter reads and a browser form next to it.
- Browser studio: `python main.py --gui` (port 8000, `--gui-port` to change it). It serves `viz/studio.html` from `gui_server.py`, runs the CLI in a subprocess, and never bypasses the export gate. The page is three columns: the left one is what you set, the canvas is the work, the right one is what you read. Both side columns are tabbed - the left has Mission, Robot, Field and Solve, the right has Result, Waypoint, Plots and Run - and every tab strip is wired by the one controller in `viz/studio.js` (`setupTabs`), so a new tab is a `role="tab"` button and a `role="tabpanel"` section and nothing else. The header's status line always carries the result (`3.70 s | 1.23 m - validated`), so a tabbed column cannot hide the answer, and a solve or a failure brings the Result tab forward by itself. Three registries carry the parts that grow: `PLOTS` (a plot is one entry; the tab strip and the drawing both come from it), `CANVAS_LEGEND` (the key to the field's colours, so it cannot go stale) and the tab controller. `docs/STUDIO_UI_INVENTORY.md` lists every control and the structure, and `tests/test_studio_inventory.py` checks the document against the page. The studio uses the simple solver only; there is no Multi-Verse toggle. `viz/studio.js` holds the mission editor: undo/redo history, the browser session in `localStorage`, the field canvas, the per-segment validation table, the robot config editor, the path-length readout, the fast-polish switch, the stop/event badges and the candidate explainer. The field canvas takes the operator's own mat image (FIRST's artwork is not ours to ship) and draws the earlier solves as faint paths, so a new trajectory can be compared with the ones before it. The field block also picks the **season**: the mission models standing on the mat come from `fields/<season>.json`, measured off FIRST's public field wireframe, and the mat's picture is still the operator's own file. The server owns the collision maths (`fields.py`): after a solve it reports where the planned path ran into a mission model, and the studio marks those places on the canvas and lists them under the result. Nothing is blocked or planned around - the collisions are only marked, and a collision shallower than the field's placement uncertainty (50 mm, because two independent readings of the same wireframe disagree by up to 100 mm) is reported as uncertain rather than as a hit. The provenance is in `research/field_maps/README.md`.  The field block offers every field in `fields/`: ours (the footprints of the models built from real parts) and RoboVibe's (the scoring areas, which cover more of the field and are read with the anchor as the corner of a shape, turned clockwise about it - with that reading the two agree to a few millimetres). `research/field_maps/convert_robovibe.py` makes RoboVibe's field file from the YAML read out of their public bundle. The studio can fetch the season's mat picture with **Download the mat**: FIRST's mat artwork is copyrighted, so it is not in the tree - the server downloads it on request from the URL the field file records (pinned to a commit) and keeps it in `mats/`, which is not tracked. The mat's size comes from the field file, so the picture and the footprints share one frame. `viz/studio.css` is local, so the studio works offline. It is the only browser UI: the WebSocket live view (`live_visualizer.py`, `viz/index.html`) was removed, and `--live` opens the studio on the given mission and solves it there.
- The studio passes `--fast-polish`, `--self-consistent` and `--sweep` when their switches are on. They are off by default, like the CLI flags.
- When a validation fails, the studio names the lever that might fix it - the other timing model, a smaller accuracy weight, or the sweep - and each is a button that re-solves. The candidates come from the validation report, which carries the accuracy weight of each candidate so a sweep's leaderboard is readable.
- The studio draws the command line's plots from the samples it already has: the velocity profiles, the wheel forces against the validator's force limit, the accelerations, the heading, and the convergence. The limits come from the server (`RobotConfig.get_max_force_at_velocity_robust`), and the convergence needs `main.py --iteration-history PATH`, which writes the solver's first guess and its solution; the first guess is drawn on the field as a dashed path.
- The studio keeps a calibrated model with the robot: `POST /api/robot/model/load` reads a `sysid_fit.json` into `calibration/<robot>.sysid_fit.json`, and every solve then passes `--sysid-fit` (which turns validation on, because the fitted plant is only used by the validator). The gain interval is the band the validator plans against. A 1 % gain band is 10 mm of position error over a 1 m path, but the controller corrects that speed error, so it barely moves the tracking error - it widens the *envelope* instead (11.8 mm on a 1 m straight, against a 20 mm threshold). A measured model therefore makes most paths fail on the envelope gate, not the tracking gate. On a *curve* the tube still crosses the validator's 50 mm guard, but that is **not** the reachable set being wide: on the S-curve the sampled reachable set is 4.09 mm against a 48 mm tube, because the validator propagates the plant open-loop and the feedback contraction is not in the tube. See `docs/research/RQ-A_tracking_error.md` findings F5 and F12, and KI-049.
- A pushed run is compared with the plan in the studio: the server builds the report with `sysid_compare.compare`, after putting the hub's pose into the plan's frame (the hub's odometry origin is where the robot sat, which is the plan's first waypoint, so the pose is rotated by the plan's first heading and moved by its first position).
- The studio can push an approved trajectory to a hub: `POST /api/push` runs `hub_deploy.py --trajectory <the solved .traj>` as a subprocess, so the export gate still holds (a failed solve has no trajectory to push). The push button is also gated on the *validator's* verdict, not on the switch on the Solve tab: a trajectory that was never validated is not an approved one, so the button stays off and the Run tab says so. The hub's console streams into the job log, the `POSE`/`EVENT` lines become the measured marker on the canvas, and the session is written to `missions/<name>.session.csv`. The robot's own files are read as text (`MISSION_EVENTS`, `WHEEL_DIAMETER_MM`, `AXLE_TRACK_MM`) because `pybricks_code/` is firmware and cannot be imported on the host.
- The studio can run the whole calibration: `POST /api/calibration/collect` pushes `pybricks_code/sysid_digital_twin.py` and captures the session, `GET`/`POST /api/calibration/sheet` reads and writes the measurement sheet as a form, and `POST /api/calibration/fit` fits the model from the session and the sheet. The files live in `calibration/<robot>.{session.csv,sheet.csv,poses.csv,sysid_fit.json}`. The fit takes the wheel radius from the session's own `META,wheel_diameter_mm`, so no drivebase profile file is needed. The fitter needs all three numbers of a row: a test that does not turn has a turn of zero.
- `docs/CALIBRATION_STUDIO_PLAN.md` is the design for the sysid loop in the studio: the measured model belongs to the robot, a pushed session can be compared but not fitted (its poses are the robot's own odometry), and the measurement sheet becomes a form. All four phases are built.
- `docs/STUDIO_HUB_PLAN.md` is the design for the studio's push-to-hub feature. Phases 1 to 3 (the push, the result overlay, the robot-file checks) are implemented; phase 4 (the sysid compare/fit loop in the studio) is not built. The push has never run against a real hub: the tests use a stand-in for the hub client.
- docs/STUDIO_3D_SIMULATOR_PLAN.md is the design for the far stretch goal: a client-side 3D WebGL (Three.js + Rapier3D Wasm) physics simulation tab in the studio with clustered LEGO mission models and articulated interactable mechanisms.
- `docs/STUDIO_UI_INVENTORY.md` lists every control, readout and generated region in the studio, panel by panel, with the counts (75 controls with an id, 147 ids in the page) and the problems a redesign has to deal with. Read it before changing the studio's markup or adding a control, and keep it in step with the page.
- The missions folder is its own git repository: the studio commits every save, lists the history and can restore an earlier version. The commits are made with a fixed identity, so no git configuration is needed on the machine, and the project repository is never touched.
- The studio's undo covers the robot config as well as the mission, and the arrow keys nudge the selected waypoint (1 cm, Shift 10 cm, Alt 1 mm). A held key is one undo step.
- The studio writes a **one-page mission report**: `viz/report.js` builds a self-contained printable document from the numbers the Result tab shows, the browser posts it to `POST /api/jobs/<id>/report`, and the server writes it next to the trajectory as `<name>_report.html` (`GET /api/jobs/<id>/report` serves it as a page). It is built from the studio's own numbers, so it cannot disagree with the screen. The report fits one A4 page for a typical mission.
- The studio also writes a **one-file project**: `format: overboard-project`, `version: 1`, holding the mission, the robot config, the solve options, the measured model and the field. **Download project** saves it and **Open project...** brings all of it back; a file that is not a project is refused with a reason rather than half-read.
- The studio runs one solve at a time. A second tab, or a reload during a solve, attaches to the running job (`GET /api/jobs/current`) instead of starting another one.
- With `--validate`, `main.py` prints one machine-readable line per run: `##OVERBOARD-VALIDATION## {json}` with the per-candidate and per-segment envelope, limit, drift and reasons. Every candidate also carries its **score vector** - `duration_s`, `envelope_cm`, `tracking_cm`, `max_excess_cm` (the biggest excess of the envelope over the local limit; negative means margin) and `peak_jerk_m_s3` - so the selection rule can be re-run offline without solving again. The studio parses it to show which part of the path failed. Nothing is written to disk on a failed validation, so the report goes to stdout, not to a file. Keep the JSON valid (`Infinity` breaks `JSON.parse`).
- Tests: `python run_tests.py` (617 tests with JAX installed). Single test: `python -m unittest tests.test_optimizer.TestTrajectoryOptimizer.test_init -v`
- Cross-check: `python research/crosscheck/compare_step.py` compares the drivetrain model with a trace from an independent rigid-body simulator. The simulator is a Linux/TypeScript project, so it runs in WSL2; `research/crosscheck/README.md` has the setup. It is measurement code: it changes nothing in the planner.
- Stress run: `python research/suite.py --count N --seed S --out DIR` writes random missions; `research/robots.py` draws random robots (the constants move, and every declared range moves with its constant, so a drawn robot is still one the ranges describe). `python research/harness.py --missions DIR --out FILE --specs default --robot-jitter 1 --robots 2` plans each mission for each robot and scores it with the production gates; each record carries the robot's factors, so `python research/analyze.py errors|robots FILE` reads it back. Measure against a pinned tree (`OVERBOARD_TREE`) when the working tree is being edited. The run of 2026-10-20 is in `docs/measurements/2026-10-20-stress/`: on random paths the **gates**, not the planner, are the binding constraint (92 % of the failures are the forward-integration and tracking gates, which are one discretisation artefact - `--self-consistent` removes every integration failure in the set), and the robot's own constants decide the verdict on 2 of 45 missions.
- Benchmarks: `python benchmark.py --mode pipeline` (also `cli`/`random`/`solver`; the default config is `examples/fll_choreo.json`). All four modes work (KI-015): the pipeline mode prints `FAILED` for a solve that did not converge, and the random mode validates against the config it actually used. `--mode solver` solves every example mission and reports the wall time, the IPOPT iteration count and the trajectory duration; add `--fast-polish` for the fast path. It is the reference table for any solver change.
- `docs/CALIBRATION_PROCEDURE.md` is the human procedure for calibrating a drivebase: what to set up, what to measure, and the commands to run. The operator drives the robot through the collector tests and measures the end pose of the five that need a tape (`odometry_straight`, `odometry_turn_cw`, `multi_stop` at three stops, `brake_from_300`, `brake_from_600`). The measurements go in a sheet keyed by test name and repeat, never by run id, so the order the tests ran in does not matter.
- The calibration-critical tests run three times each (`REPEATS` in `pybricks_code/sysid_digital_twin.py`) and the collector says which repeat a run is in with `META,repeat`. The step order is reversed on every other repeat, so a drift over the run cannot land on the step index. The fit groups the runs by repeat and reports a 95% t-interval per parameter in `<name>_between_runs` and `<name>_ci95`; with a single run there is no interval. `digital_twin.py` uses `gain_ci95` as the validator's gain band when the fit has one, and falls back to the observed min/max when it does not. The interval covers the run-to-run variation and any drift over the session, but not the error of the tape measure, which is systematic and never averages out.
- The fit measures two things the robot config could only declare, and both are inert without a fit. `drift.drift_deg_per_m` is how much the robot curves per metre when told to drive straight: the plant adds `drift_rad_per_m * v` to the heading rate, because the plan's straight segments are straight and 1 deg/m is 8.7 mm of lateral error per metre. It is a **slope, not a subtraction**: the step tests drive straight at five speeds, so the heading rate against the speed is a line whose slope is the drift and whose intercept is the gyro's bias, and a bias cannot leak into a slope the way it leaks into a subtracted one. The tape's lateral offset is an independent estimate, and the fit reports the disagreement. `stall_torque.t_max_nm` is the motor's stall torque, measured by pushing into a wall; the fit hands it to the robot config, which is where the motor lives, so the validator does not keep a second limit of its own. The motor is measured on both ends and every tool uses the measured pair: the collector's `top_speed` test lifts the robot so the motor runs free and measures the speed at which it makes no torque, the fit rejects that number when the robot reached the commanded speed instead (then the command was the limit, not the motor), and `main.py --sysid-fit` writes the measured stall torque and no-load speed into the robot config, so the optimizer, the CPU audit, the validator and the exported controller all plan against the same motor (KI-010). The model is in `drivetrain.py` and `docs/research/RQ-B_drivetrain_model.md` has the cross-check against an independent simulator.
- The step fit is a two-stage search. The first pass is a blind grid over the whole plausible range, so a local minimum cannot fool it. The second pass refines around that answer at a millisecond, and the two amplitudes of the model are solved in closed form because the model is linear in them, which also gives the covariance. The first pass alone could only land on a 10 ms boundary, and that quantisation was a floor on the reported time constant and delay.
- The wall is a reference for the distance scale that does not move and does not have to be read by hand. The `wall_homing` collector test drives the robot slowly forward from a marked start and stops when the wheels are blocked, so the distance it covered is the distance to the wall; the host turns that into the same scale the tape gives, as `distance_scale_homing`, and reports the wall and the tape side by side with their disagreement. The wall distance comes from the drivebase profile's `wall.distance_m`, measured to where the robot's centre rests against the wall, so the bumper's offset never enters. A run that never reached the wall is rejected: the robot has to be blocked while it is still commanded, which is the last row that has a command on, not the settle row the collector writes afterwards. The approach may be crooked, because the distance to a wall changes with the angle only to the second order, but the wall does not straighten the robot, so the wall cannot measure the heading and the drift still comes from the speed regression. That regression needs three points: a line through two has no degrees of freedom, and numpy refuses to scale its covariance.
- `python sysid_fit.py <session.csv> --write-sheet calibration_sheet.csv` writes the blank sheet for the tests in a session: one row per measurement the session needs, with the test name, repeat and stop filled in. `python sysid_fit.py <session.csv> --from-sheet calibration_sheet.csv --out-poses poses.csv` turns the operator's sheet into the measured-pose CSV, looking each test and repeat up in the session, converting millimetres to metres and flipping the turn (the sheet counts a turn to the right, the trajectory counts a turn to the left). It reports a row for a test that did not run and a measurement that is missing. The collector says how many poses each test needs in `META,poses`.
- `python sysid_fit.py <session.csv> --sheet calibration_sheet.csv --profile my_drivebase.json --out sysid_fit.json` fits straight from the operator's sheet, so there is no intermediate pose CSV: the same lookup and the same warnings, one command. `python sysid_fit.py <session.csv> --write-form calibration_sheet.html` writes the sheet as a self-contained form in a browser (`sheet_form.py`): one number input per measurement, the measurement convention at the top, a count of what is still missing, and a **Download CSV** button that writes the file the fitter reads. The form also takes a sheet saved earlier, so a session measured in two goes is not measured twice. It is one file with no server, so it works offline; the studio has its own version of the same form, on the server (`gui_server.py`).
- Digital-twin fit: `python sysid_fit.py <session.csv> --poses <poses.csv> --profile examples/drivebase_profile.example.json --out sysid_fit.json`. Logs come from running `pybricks_code/sysid_digital_twin.py` on the Hub; no hardware logs are checked in. Compare planned and measured poses with `python sysid_compare.py output.traj poses.csv --run-id <id>`.
- `--plot`, `--animate`, `--gui` and `--live` are blocking. `--live` and `--gui` both open the studio on `127.0.0.1:8000` (`--gui-port`); `--live` also loads the mission and solves it there. The studio never takes a port that is already in use: it tries the next free one. Keep automated runs headless.

## Test quirks (verified)
- `run_tests.py` imports the JAX test modules in a `try`; if JAX is missing it prints a warning and skips those modules. With JAX installed the suite is 617 tests, 0 skipped.
- The runner holds an **explicit list of the test classes it runs** (`test_classes()`), so a class that is not in the list is never run. `tests/test_suite_registry.py` checks that every test class in `tests/` is in that list, because a class nobody registered looks green while never running.
- The suite keeps a **test cache** (`testcache.py`, `.test_cache.json`, gitignored). A test that PASSED is skipped when nothing it reads has changed: the fingerprint covers the test module, the project modules it imports (transitively), every file it opens, every directory it lists, every project script it hands to a subprocess, every project module it imports while it runs, and the environment (Python version and the versions of numpy, casadi, jax, immrax). A failure always runs again, and a test that wrote a file inside the repository is never skipped, because another test may read what it wrote. The cache never decides that a test passed; it only says a test does not have to run again. `python run_tests.py --cache-status` says what the cache would do, `--no-cache` ignores it and runs everything, `--clear-cache` throws it away, `--durations 20` lists the slowest tests. The summary says how many tests the cache skipped and how much time that saved, so a green run never hides a skipped test. Measured: 121 s for the full suite, 20 s for a second run over the same tree (KI-032).
- The old `test_stomp_variants.py` and `test_teb_topologies.py` modules are deleted. Do not reintroduce tests for removed `MultiVerseRefiner`/`LocalSegmentOptimizer` classes.
- JAX/refinement modules: `python -m unittest tests.test_jax_heuristics tests.test_jax_ramsete tests.test_refinement_accuracy tests.test_critic_metrics`
- `tests/test_cli_ux.py` and `tests/test_gui_server.py` cover the CLI surface and the studio server. The studio tests start a real server on an ephemeral port and run one real solve.
- `tests/test_studio_honesty.py` pins the rules the studio owes the operator: the push needs a validated trajectory, a failed solve leaves no path on the field, a solve that never starts clears the last verdict, the error on the screen carries no internal path, and the `hidden` attribute actually hides (KI-030).

## Architecture and contracts
- Read `docs/HEURISTICS_AND_VERIFICATION.md` before changing the initial-guess seeds, the timing models, the candidate set, the selection rule, or the validation thresholds. It records the full heuristic inventory, the gate chain with every threshold and its source line, a ledger of the strategies that already failed (with the measured evidence), and a prioritised research agenda. Do not re-litigate a failed strategy without new evidence.
- Read `docs/research/RQ-A_tracking_error.md` before changing the optimizer's kinematics, the reference interpolation, the tracking gate or its 5 mm threshold. The tracking error is a discretisation mismatch (the optimizer's collocation, the linear reference and the plant's integration are three different discretisations of the same trajectory), not an uncertainty or physical tracking problem; the gate is currently not measuring what it claims to.
- The reference interpolates the heading, the speed, the turn rate and the Ramsete gain as independent lines, but they are coupled: the turn rate must be the derivative of the heading, and the gain must be `sqrt(w^2 + b*v^2)` of the interpolated values. The turn rate is now the derivative of the interpolated heading, in `ramsete_compact_events.py`, `ramsete_compact.py`, `ramsete_fast.py`, `ramsete.py` and `immrax_validator.py` together, so the model and the robot stay in parity (KI-027). The model takes the heading difference the short way, exactly as the firmware does, so the two agree even above 180 degrees per sample interval. Deriving the turn rate from the interpolated heading instead is worth 2-3.6x on the tracking error and turns five of the nine failing (mission, density) cells into passes; the gain inconsistency is worth nothing. See `docs/research/RQ-A_tracking_error.md` finding F7 and Fix 3.
- The gear backlash is a position uncertainty, not a velocity offset: it widens the reachable set by `backlash/2 * t` and must never be subtracted from the commanded wheel speed (KI-025). The tracking metric is position-only; the heading error is reported as `max_heading_error_rad` but is not gated, because the heading behaviour is not calibrated yet.
- The validator models the controller that **runs**, not a legacy one: `ramsete_compact.py`, `ramsete_compact_events.py` (the pushed-run entry point) and `ramsete.py` all run a synced 20 ms heartbeat, pass floats to `drive()` without rounding, and take the turn rate as the derivative of the interpolated heading (KI-027, KI-028). `immrax_validator.py` mirrors all of that, because the wheel-force hold error is proportional to the hold and the tracking gate is decided on it. `ramsete_fast.py` is the legacy path and is not what the validator models. `tests/test_firmware_events.py::TestFirmwareParity` pins the parity. The `KinematicLimiter` is still in the firmware and in no model, and the firmware's limiter still carries the old backlash model (KI-025).
- The validator has two **propagations** (`immrax_validator.py`, `PROPAGATION`). "plant" is the default: the plant is embedded and propagated and the controller is evaluated *outside* the propagation, at the tube's midpoint, with the command held for the tick - so the interval arithmetic never sees the feedback, and what it bounds is the reachable set of an open-loop plant driven by a pre-recorded command. "tick" embeds one 20 ms tick of the **closed loop** as a discrete map (`ClosedLoopTickMap`), with the controller, the robot's own pose estimate and the delayed command inside the map, and propagates the map once per tick: the map's Jacobian then carries the feedback term `dF/dx = dPhi/dx + (dPhi/du)(dN/dx)` and the tube contracts the way the robot's does. On the shipped S-curve with a +/-1 % gain band the plant propagation is cut off at the 50 mm guard (53.6 mm) and the tick map with the mixed-Jacobian gives 18.8 mm, which passes the 20 mm gate, and both contain the sampled reachable set (`docs/research/rq_a/exp20_closed_loop_tick.py`, KI-049). It needs a Jacobian inclusion - with the natural extension the closed-loop map explodes (627 mm) - and it costs 2-3x (`jac`) to 7-10x (`mjac`) the validation time, which is why it is opt-in. On the default plant it is a clear win - with the mixed-Jacobian the S-curve, the stops and the complex mission stop diverging and pass the 20 mm gate (1.88, 1.30 and 1.83 cm against 5.36, 5.31 and 5.07 cm), and every tube contains the sampled reachable set (`docs/research/rq_a/exp22_twin_propagation.py`). With the **digital twin it is worse** (5.8-12.1 cm against 5.1 cm), and the reason is the twin's *plant state*: the two wheel speeds are interval coordinates whose spread feeds the command, and the interval arithmetic counts that growth twice. It is **not** the robot's pose estimate - the control that drops the estimate is not smaller and is unsound (`docs/research/rq_a/exp23_twin_tick_belief.py`) - and carrying the estimate's *error* instead was measured and is worse too. That is why the default stays "plant".
- The propagation is now reachable from the command line: `main.py --propagation [plant|tick]` and `research/harness.py --propagation`, and every candidate in the `##OVERBOARD-VALIDATION##` line carries the `propagation` and the `inclusion` functions (KI-050). Two rules come with it. **The controller must not unpack the pose:** `x, y, theta = current_pose` is the JAX `unstack` primitive, Immrax's natural inclusion has no rule for it, and the tick map dies with "unstack not in inclusion_registry" - so the pose is read by indexing, which compiles to slice+squeeze and gives the same number. And **an envelope is never read without its model**: the report, the studio's validation note and the studio's chip tooltip all name the propagation, the same rule as `envelope_truncated`.
- `main.py` is the only CLI entry point. It defaults to `TrajectoryOptimizer` (CasADi/IPOPT); `--multiverse` selects `MasterTrajectoryOptimizer`. The Multi-Verse pipeline is bootstrap -> kinematic profile -> critic -> JAX refinement -> CasADi polish. Its refinement is **segment-preserving**: the unit of refinement is one segment, whose two endpoints are waypoints and are kept exactly, so no waypoint can be clobbered (the critic still reports two-segment windows, and each is split into the segments it covers). The refinement gives every segment the interval its own length and the robot's speed call for, and the refined timing is written back into the timestamps, so the guess carries a per-segment `dt` array.
- `--self-consistent` (simple solver only, off by default) plans a self-consistent trajectory: the position rule integrates the interval's velocity along the integrated heading with a four-node Gauss-Legendre rule instead of the trapezoidal rule, so the samples lie on the path the plan's own (v, omega) profile traces and the headings are its tangents (KI-026). The tracking error roughly halves on the curved missions: the S-curve goes from 1.31 cm to 0.55 cm (still 0.05 cm over the gate) and the events mission goes from failing both candidates to passing both (0.32 cm and 0.40 cm). The complex mission's passing candidate moves from 0.49 cm to 0.51 cm and now fails by 0.01 cm, and the stops mission gets slower. Every plan changes, so the candidate set and the seed conclusions have to be re-measured under the flag before it can become the default.
- Heavy imports are lazy: a simple solve must not import JAX, Immrax, Multi-Verse or the plotters. `main.ImmraxValidator` and `main.JAXRobotConfig` stay at module level (as `None` until `_ensure_jax_classes` fills them) so tests can patch them.
- Waypoints are dicts or `[x,y,heading]`, with optional `stop`, `event`, `error_threshold`, and `precision_mode`. An event on the final waypoint lands on the last sample; the event-capable Pybricks controllers fire it after the loop, once the robot has arrived and the drivebase has stopped (KI-012).
- `TrajectoryOptimizer.merge_conditions(waypoints, stop_waypoint_indices)` is the one place the waypoint boundary rule lives (KI-024): a waypoint is a legitimate timing boundary only when the robot stops there AND the heading is pinned; everywhere else the pieces must agree on the shared state (automatic, one variable set) and the wheel force profile must be continuous through the point. The per-segment timing model enforces the force continuity; the equal-duration model does not need it because it never changes `dt`.
- `robot_model.py` is the config abstraction: canonical `{"robot": {...}}` (`examples/fll_choreo.json`), legacy Choreo `{"config": {k: {"val": ...}}}`, or a flat dict. All three parse identically, including `robot.uncertainties`. `JAXRobotConfig` delegates to `RobotConfig` (KI-008).
- The optimizer and validator share one per-wheel force/normal-force model (`wheel_normal_forces`): lateral weight transfer only, no front/rear split (KI-010). The optimizer uses the declared worst-case cof, torque headroom, wheel radius, track width, and inertia; Immrax uses the same ranges (KI-009).
- Output is Choreo v3 (`trajectory.samples`). Keep the sample schema (`t,x,y,heading,vl,vr,omega`, forces, optional `event`/`reachability_envelope`) stable: validator, exporter, plotters, and the Pybricks runtime consume it.
- `pybricks_code/` is firmware code, not CPython (`pybricks.*`, `umath`); do not run it on the host. `complex_mission.py`/`complete_mission.py` are generated by `--export-format python`; regenerate, don't hand-edit - `mission_4_ramsete.py` and `mission_5_lambdas.py` import their `samples` and `config`, and `sysid_digital_twin.py` imports `complex_mission` for its held-out replay, so they are firmware dependencies and are tracked (KI-018). The commands are in `pybricks_code/README.md`. `mission_4_ramsete.py` imports `ramsete_fast.py` with its pathing defaults; `mission_5_lambdas.py` imports the event-capable `ramsete.py` reference. `ramsete_compact.py`/`ramsete_compact_events.py` consume `--export-format python-compact`; `ramsete_compact_events.py` is wired into `hub_runner.py`, the pushed-run entry point, and `ramsete_compact.py` is still not wired into the existing missions.
- MicroPython cannot concatenate two f-strings, so the firmware must build its output with one `%` format or one f-string per statement. This is a syntax error that only MicroPython's compiler sees, so `tests/test_hub_deploy.py::TestFirmwareCompiles` compiles every file in `pybricks_code/` with mpy-cross to catch it. Do not use adjacent f-strings in firmware code.
- The hub-to-host contract is the session format: `TEST_START <name>`, `META,key,value` (comma separated, so `META,run_id` identifies the test), `DATA`, a `t_ms,...` header, rows, `TEST_END,<n>`. A test reports its pose with `POSE,x_m,y_m,heading_deg` and an event with `EVENT,name`; `sysid_fit.poses_from_hub_session` turns the pose lines into the `poses.csv` rows (`run_id,stop,x_m,y_m,heading_deg`) the fitter and the comparator read, and a pose takes the run id of the test that was open when it was printed. The heading is counter-clockwise positive, the same convention as the planned trajectory, while the hub's `drivebase.angle()` is clockwise positive, so the fit flips one of the two when it divides them.
- `hub_runner.py` is the only hub entry point for a pushed trajectory. It imports the trajectory from `hub_mission.py` (generated by `--push-hub`, gitignored) and the hardware from `robot_config.py`; the controller it uses is `ramsete_compact_events.py`, whose `follow_trajectory` returns the final odometry pose as `(x, y, heading)` in metres and radians. Keep the runner's `POSE` and `EVENT` line formats: `sysid_compare.py` and the hub session files depend on them. Event actions live in the runner's `MISSION_EVENTS` dict; `robot_config.py` stays hardware-only.
- Root-level `.traj`, `*_controller.json`, `*_stats.json`, and `test_output*` are generated artifacts, not source. `sysid_fit.py` is the host-side parser/fitter for `pybricks_code/sysid_digital_twin.py` logs; it does not run on the Hub. `hub_deploy.py` is the host-side push client for the Pybricks BLE/USB profile; it talks to a hub with `pybricksdev` and never imports it at module level, so a plain solve does not pay for it. `sysid_collect.py` is the one-command SysId loop: push the collector, capture the session, convert the poses, fit.
