# AGENTS.md

Python CLI/library for time-optimal trajectories of a LEGO/FLL differential-drive robot (CasADi + IPOPT), plus robot-side Pybricks code. Flat modules, no packaging: run every command from the repo root.

This file is the index: the rules that must not be missed, and where the rest lives. The long form - measurements, thresholds, feature tours, the reasons a rule exists - is in `docs/AGENT_OPS.md`, one section per topic named below. Read the section a task needs, not the whole file.

## Read first

- `KNOWN_ISSUES.md` is the source of truth for risky paths. Open: KI-004 (the seed provider), KI-020 (hardware calibration and digital-twin validation). Mitigated: KI-032 (the test cache). Everything else in KI-001..KI-052 is fixed. Cite KI IDs; do not silently "fix" an open one unless asked.
- `--validate` is a hard gate, and the validation model is not yet a full digital twin (KI-020).
- `docs/HEURISTICS_AND_VERIFICATION.md` before changing the initial-guess seeds, the timing models, the candidate set, the selection rule or the validation thresholds. It holds the strategy ledger: do not re-litigate a failed strategy without new evidence.
- `docs/research/RQ-A_tracking_error.md` before changing the optimizer's kinematics, the reference interpolation, the tracking gate or its 5 mm threshold.
- The Multi-Verse pipeline is a **seed provider**, not a second solver: `--refine` puts its refined trajectory into the candidate set, and it is opt-in (KI-004). Where a doc and the tree disagree, the source is the authority.
- Full text of this section: `docs/AGENT_OPS.md` §Read first.

## Commands

- Install the core path: `pip install -r requirements.txt` (solver and studio). `--validate`, `--multiverse` and `--push-hub` also need `pip install -r requirements-optional.txt` (jax, jaxopt, immrax, pybricksdev). `install.bat` (Windows) or `sh install.sh` creates `.venv` with both and runs the check; `start_studio.bat` / `sh start_studio.sh` start the studio with it. The `.bat` files must keep CRLF line endings (`cmd.exe` cannot find a batch label in an LF file, and `install.bat` calls a subroutine); the `.sh` files must stay LF. Version notes: §Install.
- `python main.py --doctor` reports the Python version, every package, the example files, the output directory and the ports, with the install command for anything missing. It works on a clean machine because `main.py` reports the install command instead of an ImportError when the core packages are missing. Run it first when something does not work.
- Quick, predictable run:
  `python main.py -w examples/example_straight.json -o output.traj`
- The simple CasADi solver is the default; `--multiverse` opts into the experimental pipeline and `--simple` is a deprecated alias. The Multi-Verse path keeps its own accuracy-weight ladder (`base, base+2.0, ...`) because seed and timing plumbing live only in `TrajectoryOptimizer`; flags marked *simple solver only* are refused by `--multiverse`.
- `--refine` (simple solver only, needs JAX) adds the seed provider's refined trajectory to the candidate set. Off by default: it is a cheaper way to reach the stock set's speed, not a better one, and it rescues nothing (KI-004). Detail: §Solve options.
- The default candidate set mixes the two timing modes - candidate 1 is the equal-duration baseline, candidate 2 the per-segment baseline, then the remaining seeds alternate. `--candidates N` (default 2, max 5) sets the count; `--uniform-dt` / `--per-segment-dt` force one mode. The per-segment mode is the general model (equal `dt_i` recovers the equal-duration solution) and both are held to the same wheel-jerk discipline, so `--accuracy-weight` means the same thing in either (KI-022). **Do not force a mode silently.**
- A waypoint is a legitimate timing boundary only when the robot stops there AND the heading is pinned; everywhere else the pieces stay linked, and the per-segment model requires the wheel acceleration - and so the wheel force - to be continuous through the point (KI-024). `TrajectoryOptimizer.merge_conditions(waypoints, stop_waypoint_indices=None)` is the one place that rule lives.
- When a run produces nothing usable - no candidate passes the gates, or (without validation) none converged - the CLI tries the other seeds as a rescue before giving up (KI-048). A rescue candidate is selected only when the candidate set itself produced nothing that passed; it costs nothing when the plan works, and one parallel round of solves when it does not.
- `--fast-polish` runs the fast solve path (a 200-iteration warm budget, then a cold finish from the original guess, then the unbudgeted pass if the cold finish fails). Off by default; a mission that converges inside the budget returns a bit-identical trajectory, and one that needs the cold finish lands on a slightly different optimum. §Solve options.
- `--sweep` (simple solver only) adds the timing-mode x accuracy-weight grid to the candidate set - ten candidates instead of two. It never removes the default candidates, so it can only add options. Off by default. §Solve options.
- `--force-weight` (simple solver only, off by default) adds a third objective term: the time integral of squared wheel-force utilisation against the stall force and the traction limit. The hard per-wheel limits still apply; the term prices the force. Weight 0 by default.
- The optimizer also takes three parameters the command line does not expose: `cost_metric` (`"jerk"` or `"discretization"`), `epigraph_constraints` (the force bound as four linear inequalities instead of a `sqrt`) and `sample_weights` (a per-sample weight on the smoothness or discretisation term). `TrajectoryOptimizer.solve` reads them. §Solve options.
- `--surrogate-polish` and `--unified` (simple solver only) are the two opt-in experimental pipelines: a 5-layer surrogate-to-truth chain, and the 3-Pillar Unified Trajectory Engine. Neither is the default path and both are off by default. §Solve options.
- `--preset fast|balanced|safe` fills in only the options the user did not set: fast = 1 candidate without validation, balanced = the defaults, safe = 3 candidates with `--validate` and a controller export. Explicit flags always win.
- `--validate` gates every output and the exit code, and requires JAX/Immrax. It solves the `--candidates` set (parallel when validating), validates each, and selects a passing one by the lowest 5-part path fitness score (reachability spread at the stops, slip risk, RMS wheel force, tracking error, run time - all in seconds; envelope and duration break ties). The fitness score needs the Immrax report, so without one the rule is the smallest envelope, then the shortest duration. Without `--validate`, only the first candidate is solved. **If validation fails, no `.traj`, controller, Python file or `_stats.json` is written.** §Validation.
- `--propagation [plant|tick]` chooses the reachability model the envelope gate uses (KI-049, KI-050). "plant" is the default: the plant is propagated open-loop and the controller is evaluated outside the tube. "tick" embeds one closed-loop tick (controller, pose estimate and delayed command inside the map), so the tube contracts like the robot's - but it needs a Jacobian inclusion and costs 2-3x (`jac`) to 7-10x (`mjac`) the validation time. `research/harness.py` takes the same flag. **An envelope is never read without its model**: every candidate carries `propagation` and `inclusion`. §Validation.
- `--validate --export-format controller` writes `<output>_controller.json`; `--export-format python` writes `<output>.py` (legacy list format); `python-compact` writes a packed module for `ramsete_compact.py` / `ramsete_compact_events.py`; `--benchmark` writes `<output>_stats.json` after the export gate.
- `--push-hub` writes the packed trajectory to `pybricks_code/hub_mission.py` and pushes `pybricks_code/hub_runner.py`, with `robot_config`, the controller and the mission bundled by pybricksdev. `--hub-conn ble|usb`, `--hub-name`, `--hub-log`; the runner prints `POSE,x_m,y_m,heading_deg` and `EVENT,name`. It needs `pybricksdev`; a plain solve never imports it. §Export.
- Bluetooth discovery goes through `hub_ble.py`, which probes what is nearby the way the Pybricks IDE does - Windows does not report the advertised service UUID and local name the way pybricksdev's filter wants (KI-033). `python hub_deploy.py --list-hubs` is the IDE's device picker. The CLI, `--push-hub`, `sysid_collect.py` and the studio's push all use it.
- `python hub_deploy.py <script.py> [--conn ble|usb] [--name NAME] [--out session.csv]` pushes any script and saves its console output as it arrives, so a dropped link costs the last test, not the session. `--list-hubs` pushes nothing.
- `python sysid_collect.py --conn ble [--profile FILE]` collects a SysId session and fits it in one command (push, capture, `poses.csv`, `sysid_fit.json`); the operator still presses the hub button between tests. The poses are the hub's own odometry, so the distance scale, heading scale and brake slip stay at their defaults; the actuator fit needs no measurement. §Export.
- Browser studio: `python main.py --gui` (port 8000 on `127.0.0.1`, `--gui-port` to change it, next free port if busy). It serves `viz/studio.html` from `gui_server.py`, runs the CLI in a subprocess and **never bypasses the export gate**. The studio uses the simple solver only, and runs one solve at a time - a second tab or a reload attaches to the running job (`GET /api/jobs/current`). §The browser studio.
- The studio's tabs are wired by one controller (`setupTabs`); `PLOTS` and `CANVAS_LEGEND` are the two registries that carry what grows. `docs/STUDIO_UI_INVENTORY.md` lists every control and `tests/test_studio_inventory.py` checks the document against the page - read it before changing the markup or adding a control, and keep it in step.
- The studio's push button is gated on the *validator's* verdict, not on the switch: `POST /api/push` runs `hub_deploy.py --trajectory <solved .traj>`, so a trajectory that was never validated stays unpushable. The calibration loop is `POST /api/calibration/collect|sheet|fit`, with files in `calibration/<robot>.*`. The one-page report (`viz/report.js` -> `<name>_report.html`) and the one-file project (`format: overboard-project`, `version: 1`) are built from the studio's own numbers.
- With `--validate`, `main.py` prints one machine-readable line per run: `##OVERBOARD-VALIDATION## {json}` with the per-candidate and per-segment envelope, limit, drift, reasons, the accuracy weight of each candidate and its score vector (`duration_s`, `envelope_cm`, `tracking_cm`, `max_excess_cm`, `peak_jerk_m_s3`, `fitness_s` and its parts), so the selection rule can be re-run offline. The studio parses it. **Keep the JSON valid** (`Infinity` breaks `JSON.parse`). Nothing is written to disk on a failed validation, so the report goes to stdout only.
- `docs/CALIBRATION_PROCEDURE.md` is the human procedure for calibrating a drivebase. `docs/CALIBRATION_STUDIO_PLAN.md` is the design for the sysid loop in the studio, `docs/STUDIO_HUB_PLAN.md` for the push (phases 1-3 built; the push has never run against a real hub - the tests use a stand-in), and `docs/STUDIO_3D_SIMULATOR_PLAN.md` for the far stretch goal.
- Calibration critical facts: the calibration-critical tests run three times each with the step order reversed on every other repeat, and the fit reports a 95 % t-interval per parameter; the drift is a **slope, not a subtraction**; the motor's stall torque and no-load speed are measured on both ends and `main.py --sysid-fit` writes them into the robot config, so the optimizer, CPU audit, validator and exported controller plan against the same motor (KI-010). Detail and commands: §Calibration.
- Tests: `python run_tests.py` (634 tests with JAX installed). Single test: `python -m unittest tests.test_optimizer.TestTrajectoryOptimizer.test_init -v`
- Cross-check: `python research/crosscheck/compare_step.py` compares the drivetrain model with an independent rigid-body simulator (WSL2; `research/crosscheck/README.md`). It is measurement code and changes nothing in the planner.
- Stress run: `python research/suite.py --count N --seed S --out DIR`, then `python research/harness.py --missions DIR --out FILE`, read back with `python research/analyze.py errors|robots FILE`. Measure against a pinned tree (`OVERBOARD_TREE`) when the working tree is being edited. §Research.
- Benchmarks: `python benchmark.py --mode pipeline|cli|random|solver` (default config `examples/fll_choreo.json`). All four modes work (KI-015); `--mode solver` is the reference table for any solver change, and `--fast-polish` adds the fast path.
- `--plot`, `--animate`, `--gui` and `--live` are blocking; `--gui` and `--live` both open the studio (`--live` loads the mission and solves it there). Keep automated runs headless.

## Test quirks (verified)

- `run_tests.py` imports the JAX test modules in a `try`; without JAX it prints a warning and skips them. With JAX the suite is 634 tests, 0 skipped.
- The runner holds an **explicit list of the test classes it runs** (`test_classes()`), so a class that is not in the list never runs. `tests/test_suite_registry.py` checks that every test class in `tests/` is listed.
- The suite keeps a **test cache** (`testcache.py`, `.test_cache.json`, gitignored). A test that PASSED is skipped when nothing it reads has changed; a failure always runs again, and a test that wrote a file inside the repository is never skipped. The cache never decides that a test passed - it only says a test does not have to run again. `--cache-status`, `--no-cache`, `--clear-cache`, `--durations 20`. Measured 121 s cold, 20 s warm (KI-032). §Research.
- The old `test_stomp_variants.py` and `test_teb_topologies.py` modules are deleted. Do not reintroduce tests for removed `MultiVerseRefiner` / `LocalSegmentOptimizer` classes.
- JAX/refinement modules: `python -m unittest tests.test_jax_heuristics tests.test_jax_ramsete tests.test_refinement_accuracy tests.test_critic_metrics`
- `tests/test_cli_ux.py` and `tests/test_gui_server.py` cover the CLI surface and the studio server (a real server on an ephemeral port and one real solve). `tests/test_studio_honesty.py` pins what the studio owes the operator (the push needs a validated trajectory, a failed solve leaves no path on the field, an error carries no internal path, `hidden` actually hides - KI-030).

## Architecture and contracts

- `main.py` is the only CLI entry point. It defaults to `TrajectoryOptimizer` (CasADi/IPOPT); `--multiverse` selects `MasterTrajectoryOptimizer`. The Multi-Verse pipeline is bootstrap -> kinematic profile -> critic -> JAX refinement -> CasADi polish, and its refinement is **segment-preserving**: the unit is one segment, whose two endpoints are waypoints and are kept exactly, so no waypoint can be clobbered. §Planner internals.
- `TrajectoryOptimizer.solve` **splits the path** at the waypoints where the robot stops AND the heading is pinned (the merge conditions' full timing boundaries) and solves each piece as its own NLP, trying the seeds and keeping the cheapest. It is opt-out (`split_at_boundaries=False`).
- The **sample count follows the path**: `get_segment_sample_counts` splits the budget in proportion to arc length (at least three samples each), and the code carries `waypoint_sample_indices` and `stats["segment_samples"]` so a sample maps back to its waypoint. Seeds and the objective follow that layout; a measurement must say which layout it was taken on.
- `--self-consistent` is the default everywhere (CLI and `TrajectoryOptimizer.solve`); `--no-self-consistent` restores the trapezoidal rule. The position rule integrates the interval's velocity along the integrated heading with a four-node Gauss-Legendre rule, so the samples lie on the path the plan's own (v, omega) profile traces and the headings are its tangents (KI-026, KI-051, KI-052). §Planner internals.
- The reference interpolates the heading, the speed, the turn rate and the Ramsete gain as independent lines, but they are coupled: the turn rate must be the derivative of the interpolated heading and the gain must be `sqrt(w^2 + b*v^2)` of the interpolated values. That is what `ramsete_compact_events.py`, `ramsete_compact.py`, `ramsete_fast.py`, `ramsete.py` and `immrax_validator.py` all do, so model and robot stay in parity (KI-027). The model takes the heading difference the short way, as the firmware does.
- The validator models the controller that **runs**: a synced 20 ms heartbeat, floats to `drive()` without rounding, and the turn rate as the derivative of the interpolated heading (KI-027, KI-028). **There is one implementation of the controller in the firmware** - `ramsete.py` holds the odometry, the Ramsete maths and the loop; `ramsete_fast.py` delegates to it and `ramsete_compact.py` delegates to `ramsete_compact_events.py` with events off - so a second copy cannot drift. `tests/test_firmware_events.py::TestFirmwareParity` pins it. The firmware `KinematicLimiter` uses the per-wheel traction limit with lateral weight transfer (KI-010) and the robot's own fallback numbers, and applies no backlash: backlash is a position uncertainty in the reachable set (KI-025), never a velocity offset and never a command subtraction.
- The validator has two propagations (`immrax_validator.py`, `PROPAGATION`). "plant" is the default and what the numbers in `docs/measurements/2026-10-20-tick/` compare against; "tick" is opt-in. The tick map's Jacobian needs the mixed inclusion - the natural extension explodes - and the pose must be read by indexing, never unpacked (`x, y, theta = pose` is `unstack`, which has no inclusion rule). §Validation.
- `robot_model.py` is the config abstraction: canonical `{"robot": {...}}` (`examples/fll_choreo.json`), legacy Choreo `{"config": {k: {"val": ...}}}` or a flat dict, all parsing identically including `robot.uncertainties`. `JAXRobotConfig` delegates to `RobotConfig` (KI-008).
- The optimizer and validator share one per-wheel force/normal-force model (`wheel_normal_forces`): lateral weight transfer only, no front/rear split. The optimizer uses the declared worst-case cof, torque headroom, wheel radius, track width and inertia; Immrax uses the same ranges (KI-009, KI-010).
- Heavy imports are lazy: a simple solve must not import JAX, Immrax, Multi-Verse or the plotters. `main.ImmraxValidator` and `main.JAXRobotConfig` stay at module level (`None` until `_ensure_jax_classes` fills them) so tests can patch them.
- Waypoints are dicts or `[x,y,heading]`, with optional `stop`, `event`, `error_threshold` and `precision_mode`. An event on the final waypoint lands on the last sample and fires after the loop, once the robot has arrived and the drivebase has stopped (KI-012).
- Output is Choreo v3 (`trajectory.samples`). Keep the sample schema (`t,x,y,heading,vl,vr,omega`, forces, optional `event` / `reachability_envelope`) stable: validator, exporter, plotters and the Pybricks runtime consume it.
- `pybricks_code/` is firmware code, not CPython (`pybricks.*`, `umath`); do not run it on the host. `complex_mission.py` / `complete_mission.py` are generated by `--export-format python` - regenerate, do not hand-edit; `sysid_digital_twin.py` imports `complex_mission`, so they are tracked dependencies (KI-018). `ramsete_compact.py` / `ramsete_compact_events.py` consume `--export-format python-compact`, and `ramsete_compact_events.py` is wired into `hub_runner.py`. §Planner.
- MicroPython cannot concatenate two f-strings, so the firmware must build its output with one `%` format or one f-string per statement. `tests/test_hub_deploy.py::TestFirmwareCompiles` compiles every file in `pybricks_code/` with mpy-cross to catch it.
- The hub-to-host contract is the session format: `TEST_START <name>`, `META,key,value`, a `DATA` block with a `t_ms,...` header, `TEST_END,<n>`; a test reports `POSE,x_m,y_m,heading_deg` and `EVENT,name`, and a pose takes the run id of the test that was open when it was printed. `sysid_fit.poses_from_hub_session` turns poses into the `poses.csv` rows the fitter and comparator read. The planner's heading is counter-clockwise positive while `drivebase.angle()` is clockwise positive - the fit flips one. Never break the `POSE` / `EVENT` line formats.
- `hub_runner.py` is the only hub entry point for a pushed trajectory; it imports the trajectory from the generated `hub_mission.py` (gitignored) and the hardware from `robot_config.py`. `follow_trajectory` returns the final odometry pose as `(x, y, heading)`. Event actions live in the runner's `MISSION_EVENTS`; `robot_config.py` stays hardware-only.
- Root-level `.traj`, `*_controller.json`, `*_stats.json` and `test_output*` are generated artifacts, not source. `sysid_fit.py` is the host-side parser/fitter for `sysid_digital_twin.py` logs; it never runs on the Hub.
