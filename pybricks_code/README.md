# Snowbotics Pybricks Template

Starting point for FLL robotics teams using Pybricks on the LEGO Spike Prime Hub.

---

## Quick Start

**Step 1 — Install Pybricks firmware on your Hub**
Go to [code.pybricks.com](https://code.pybricks.com/), connect your Hub, and follow the on-screen instructions to install the firmware.

**Step 2 — Set your motor and sensor ports**
Open `robot_config.py`. Find the `HARDWARE DEFINITIONS` section and change the port letters to match where your motors and sensors are physically plugged in on your robot.

**Step 3 — Run the robot**
Open `robot.py` in the Pybricks IDE and click **Run**. The hub's **Left/Right** buttons pick a program and the **Center** button runs it: **1** follows the trajectory the host pushed last, **2** runs the SysId data-collection protocol.

That's it! You're running code on the robot.

## Known limitations

- **Events on the final waypoint fire after the drivebase stops.** The follower stops before the last sample, so `ramsete.py` and `ramsete_compact_events.py` fire that last event after the loop, once the robot has arrived (KI-012). An action that must run before the robot settles should still be scheduled from the mission instead.
- There is **one** controller implementation, in `ramsete.py`: the odometry, the Ramsete maths, the `KinematicLimiter` and the synced 20 ms loop. `ramsete_fast.py` is the list-of-dicts pathing entry point and delegates to it; `ramsete_compact.py` and `ramsete_compact_events.py` are the packed-trajectory alternatives for `--export-format python-compact`, and `ramsete_compact.py` delegates to `ramsete_compact_events.py` with the events off. So a second copy of the controller cannot drift away from the one that runs (KI-028). Missions import the controller they need; `robot_config.py` is hardware-only.
- `complex_mission.py` is generated by `--export-format python`. Regenerate it from the optimizer instead of hand-editing it: `sysid_digital_twin.py` imports it for its held-out replay, so it is tracked. From the repository root:

  ```bash
  # the complex mission. Passes the gates.
  python -m overboard.main -c examples/fll_choreo.json -w examples/example_complex_mission.json \
    -o pybricks_code/complex_mission.traj --export-format python --validate --candidates 2

  # the event demo. This mission does NOT pass the gates (the envelope and the
  # tracking error on the last two segments), so it is exported without
  # --validate. It demonstrates the lambda event API; it is not a plan to drive.
  python -m overboard.main -c examples/fll_choreo.json -w examples/example_complete.json \
    -o pybricks_code/complete_mission.traj --export-format python --self-consistent
  ```

  The `.traj` files are intermediates and are ignored by git. The generated
  `.py` carries the robot config it was planned against, so a regenerated
  copy is visible in the diff (KI-018).
- This code is firmware code, not CPython. It uses `pybricks.*` and `umath`; run it on the Hub, not with the host Python.

## Compact trajectory exports

The default `--export-format python` writes a list of dicts and is read by
`ramsete_fast.py` / `ramsete.py`. For long paths,
`--export-format python-compact` writes the same samples as one packed
`bytes` object:

- 4-byte little-endian header: `<HH` version and sample count
- 24 bytes per sample: `<6f` `t, x, y, heading, v, omega`
- events are separate: `events = ((sample_index, "name"), ...)`

This avoids the list-of-dicts allocation on the Hub. The plain follower is
`ramsete_compact.py` (20 ms loop, no event handling). The event-capable
follower is `ramsete_compact_events.py`; it holds the packed-trajectory loop
and imports `Odometry`, `RamseteController`, and `KinematicLimiter` from
`ramsete.py`, and accepts the same `config` plus `events` and `event_map`
arguments. `ramsete_compact.py` is a thin wrapper over it with the events
switched off.

```python
from pybricks.tools import run_task
from ramsete_compact_events import follow_trajectory
from my_generated_mission import config, events, samples

async def main():
    await follow_trajectory(
        drivebase,
        samples,
        config=config,
        events=events,
        event_map={"release": release_attachment},
    )

run_task(main())
```

Both controllers assume the robot starts at the first sample pose. An event on
the final sample is fired after the loop, once the robot has arrived and the
drivebase has stopped (KI-012).

## Pushing a trajectory to the hub

The hub can be driven from the host, without the Pybricks IDE. The host writes
the packed trajectory to `hub_mission.py` and pushes `hub_runner.py`; the
push bundles the local imports, so `robot_config.py`, `ramsete_compact_events.py`,
`ramsete.py` and `hub_mission.py` all travel with it.

```bash
pip install pybricksdev
python -m overboard.main -w mission.json --push-hub --hub-log session.csv
```

Over Bluetooth, the host finds the hub the way the Pybricks IDE finds it: it
looks at what the adapter can see and probes the devices until one answers as
a Pybricks hub. Windows does not report the advertised service UUID and the
local name in the shape a strict filter wants, so the advertisement alone
does not identify a hub (KI-033). To see what is around before a push:

```bash
python -m overboard.deploy.hub_deploy --list-hubs
```

It prints every device the adapter can see and marks the hub. `--name` (or
`--hub-name`) still works: the named device is asked first, so two hubs
nearby are no longer a guess.

`hub_runner.py` follows the trajectory with `ramsete_compact_events.py` and
prints the result:

```
Battery Voltage: 8100 mV
Mission Start: compact event loop...
EVENT,lower_arm
Trajectory complete.
POSE,0.4821,-0.0033,1.20
```

`POSE,x_m,y_m,heading_deg` is the measured final pose, so it becomes a row of
the `poses.csv` that `overboard.sysid.compare` reads. An exported event with no
action is reported as `EVENT,name` and fires nothing; add the actions for
your robot in `MISSION_EVENTS` in `hub_runner.py` (the archived
`archive/mission_5_lambdas.py` shows the same idea with a nested table).

To run something else on the hub and capture its console output, push any
script:

```bash
python -m overboard.deploy.hub_deploy pybricks_code/sysid_digital_twin.py --out session.csv
```

## Digital-twin calibration data

`sysid_digital_twin.py` collects the hardware logs used to fit the JAX/Immrax
plant model. It wraps `DriveBase` externally, so the selected controller keeps
its normal memory and 20 ms timing profile. Replay uses `ramsete_fast.py` for
list-format modules and `ramsete_compact.py` for packed modules.

1. Run `sysid_digital_twin.py` on the Hub. Follow the setup prompts and save the
   complete console output as one `.csv` file.

   The host can push the collector and capture the session for you, without
   the Pybricks IDE:

   ```bash
   python -m overboard.sysid.collect --conn ble \
       --profile examples/drivebase_profile.example.json \
       --session session.csv --sheet calibration_sheet.csv
   ```

   That pushes the collector, writes the session as it arrives, turns the
   `POSE` lines into `poses.csv`, writes the measurement sheet (the CSV and a
   form in a browser next to it), and fits the model. The operator still
   presses the hub button when each test asks for it.

   **For the full human procedure, see
   [docs/CALIBRATION_PROCEDURE.md](../docs/CALIBRATION_PROCEDURE.md).** It
   has the setup for every test, the measurement convention, and the
   troubleshooting.

2. Measure the final pose for each run and record it in `poses.csv`:

   ```csv
   run_id,stop,x_m,y_m,heading_deg
   1,0,0.998,0.002,0.0
   ```

   `run_id` is printed in each block as `META,run_id`. For `multi_stop`, add one
   row per stop in order, with `stop` set to 0, 1, 2. If you combine multiple
   session files, prefix the printed ID with the file stem (for example
   `session1:1`).

   The hub reports its own pose as a `POSE,x_m,y_m,heading_deg` line, and the
   host turns those into this file. That pose is the robot's odometry, not a
   measurement, so the distance scale, the heading scale and the brake slip of
   the fit have no ground truth: replace those rows with tape measurements to
   calibrate them. The actuator part of the fit needs no measurement.

   To keep the measurements by test name and repeat instead of by run id, fill
   in a sheet and let the host do the bookkeeping:

   ```bash
   python -m overboard.sysid.fit session.csv --write-form calibration_sheet.html
   # the operator fills in x_mm, y_mm and turn_right_deg in the browser form
   # and downloads the CSV
   python -m overboard.sysid.fit session.csv --sheet calibration_sheet.csv \
       --profile examples/drivebase_profile.example.json --out sysid_fit.json
   ```

   `--write-form` writes the sheet as a form in a browser: one row per
   measurement, the convention at the top, and a **Download CSV** button that
   writes the file the fit reads. `--write-sheet` writes the same sheet as a
   plain CSV, and `--from-sheet ... --out-poses poses.csv` writes the
   measured poses as a file of their own.
3. From the repository root, fit the model with a minimal drivebase profile:

   ```bash
   python -m overboard.sysid.fit logs/session.csv --poses poses.csv \
       --profile examples/drivebase_profile.example.json --out sysid_fit.json
   ```

   Copy `examples/drivebase_profile.example.json` and change `wheel_radius_m`
   and `track_width_m`. `--robot-config examples/fll_choreo.json` still works
   for a full robot config, and `--wheel-radius` overrides the profile.

4. Use the fit in the host validator:

   ```bash
   python -m overboard.main -c examples/fll_choreo.json \
       -w examples/example_straight.json -o output.traj \
       --validate --sysid-fit sysid_fit.json
   ```

5. Compare the planned trajectory with the measured poses:

   ```bash
   python -m overboard.sysid.compare output.traj poses.csv --run-id 4 \
       --profile examples/drivebase_profile.example.json
   ```

   For a multi-stop trajectory, pass the waypoint file or the trajectory
   sample indices:

   ```bash
   python -m overboard.sysid.compare output.traj poses.csv --run-id 12 \
       --waypoints examples/example_with_stops.json
   ```

   The comparator also accepts a predicted-pose CSV with `t,x,y,heading`
   instead of a `.traj`, and reports a warning when the profile geometry does
   not match the trajectory config.

The comparison prints predicted vs measured stop/final poses, position and
heading errors, and whether each measured pose is inside the reachability
envelope. It is a diagnostic only; the 5 mm/2 cm gate is unchanged.

The fit is not yet a full digital twin: it covers first-order actuator response,
the odometry scale, and a bounded braking-slip estimate. The validator applies
the straight-line actuator gain, time constant, command delay, an acceleration
limit, the robot's own odometry belief, and the braking shortfall (while braking,
the wheels turn further than the robot travels, so the plant slows the ground
truth). The 5 mm tracking and 2 cm envelope thresholds stay unchanged until
hardware validation.
