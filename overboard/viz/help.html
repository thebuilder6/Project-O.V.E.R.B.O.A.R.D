OVERBOARD Studio - start here

Plan how a LEGO differential-drive robot should move, check the plan against what the robot can actually do, and only then let it leave the machine. This page is the short version: the journey, what the numbers mean, and what to do when a plan fails.

The journey: draw, solve, read, run

  1. Draw a path. Double-click the field to add waypoints; drag one to move it. Tick Stop here where the robot must halt. The Mission tab names and saves it.
  2. Press Solve. The planner finds the fastest plan for the path and - with Validate before export on in the Solve tab - checks it against your robot before anything is written.
  3. Read the verdict. The Result tab opens with the score first: what it means, and what to do next. The detail is behind Advanced when you want it.
  4. Run it. The Run tab says whether the plan is ready, and gives you the files. Pushing it to the hub is optional.

Each tab shows the everyday controls; anything expert sits behind an Advanced reveal, so you never have to open one to finish the journey.

What the score means (and what it does not)

After a checked solve, the Result tab shows a decision score from 0 to 100 - the planner's judgement of the plan in decision units, not a probability of hardware success. A 90 does not mean a 90% chance of working; it means this plan scores better than one that scores 80, on the profile you picked.

CategoryWhat it says
PhysicalHow hard the wheels work against the force and slip limits.
AccuracyHow close the robot stays to the planned path - the drift, against the drift budget.
Motion QualityHow smooth the drive is - how abruptly the wheels change force (jerk).
DurationHow fast it is, against your target run time.

The scoring profile in the Solve tab is what the score values: Precision (accuracy first), Balanced (even), or Speed (time first).

What the checks mean

  • Drift budget (the envelope): how far the robot may stray from the planned path. The check measures it as a tube around the path - everywhere the robot could reasonably be - and refuses a plan whose tube is wider than the budget. Each waypoint can ask for a tighter budget of its own.
  • Tracking error: how far the robot strayed while driving the plan, under the controller that will run on the hub.
  • Force and slip limits: how hard the wheels may be pushed at all, and sideways before they slide. A plan that needs more than the robot has is refused, however fast it is.

A pass is a model prediction, not a measurement. The validator is not yet a full digital twin: motor, odometry and slip are modelled only in part. Treat the drift budget as a budget, and check the first runs by hand.

What a verdict means

VerdictReading
PassedEvery check held: drift budget, tracking, force, slip. This is the verdict that is ready to run and can be pushed to the robot.
Accepted despite a known problemThe plan failed a check, and you chose to keep it because its score was at or above your accept-score. It is not a passed plan. You can push it, deliberately, on that understanding.
FailedNothing is exported. The message names what failed and by how much.
Best effortThe plan's only failure was the drift budget or tracking, so the best path is kept to look at. It is never approved for the robot.
Not validatedThe solve ran without the checks. The path exists on the field; the push stays off. Turn validation on and solve again before driving it.
Structural failureThe plan itself is broken - the solver did not finish, the check crashed, or the path is incomplete. Nothing is written at all.

When a plan fails

  1. Read the plain line under the score: it names the reason and the next step.
  2. Open Advanced on the Result tab for the per-segment numbers, and press a Try button - each one pulls the lever the numbers point at and solves again, and the studio records what that lever measured.
  3. Or change the mission: a tighter turn, a stop, a shorter path. The solver can only plan the path you drew.

Every number the studio gives you after a solve is measured, never estimated in advance. The lever table only grows when a solve has finished.

Where your files are

Missions, calibration and generated firmware are kept outside the program, so an update never touches them. OVERBOARD_HOME points the whole folder somewhere else.

SystemFolder
Windows%LOCALAPPDATA%\OVERBOARD
macOS~/Library/Application Support/OVERBOARD
Linux~/.local/share/OVERBOARD
  • missions/ - saved missions, one JSON each, under version control.
  • calibration/ - the SysId session, the sheet, the fit and the digital twin.
  • pybricks_code/ - the firmware, including the generated hub_mission.py and your robot_config.py.
  • mats/ - the field artwork, downloaded on request.
  • docs/ - every document from the project, including the calibration procedure and the design notes. The desktop app seeds a copy here, so the manual travels with the program.

A trajectory is written into the folder of the solve that produced it, and is listed with the other files under Run.

Calibration

Before you trust a plan, measure the real robot. The guided SysId page (/sysid) walks the loop in four steps - collect on the hub, measure with the tape, fit, compare before against after - and keeps every raw artifact per robot in calibration/: the full session, the sheet with the weigh-in, the poses and the fit with its intervals. A dropped Bluetooth tail is flagged, never silently cut. Finish preselects the new fit in the main Solve tab ("Plan against the measured model") and solves nothing by itself. The Collect step lists every suite test: pick a subset to redo one test out of order (in suite order, dependencies first), each with its setup hint, and a redo appends to the session and supersedes the attempt it replaces. While it runs, each hub prompt appears on the page with entry boxes for the numbers it asked for. A pushed trajectory session is compare-only and is never fitted. Until calibration is done the checks describe the example robot, not yours. docs/CALIBRATION_PROCEDURE.md walks through it step by step.

Pushing to the robot (optional)

The Run tab can push the plan to the hub and drive it. It needs the robot on and connected over Bluetooth or USB - Scan for hubs finds it - and it refuses a trajectory that is not approved, or a mission that changed after the solve. A hub is never required: download the files and run the plan another way. After the drive, the hub reports its own odometry back, and the studio compares it with the plan.

Command line

The same program without the browser. Every option the studio sets has a flag:

python -m overboard.main -w mission.json -o out.traj --validate
python -m overboard.main --doctor
python -m overboard.main --gui

A validated run ends with a short plain-language verdict block (score, what it means, the next step) and one machine-readable line for tools. --doctor prints the Python, the packages, the example files, the folders and the ports, with the command that fixes anything missing. Run it first when something does not work.

If something goes wrong

  • The solve never finishes. Cancel, cut the points per piece of path under Solve > Advanced, or use the fast preset; a long mission with many candidates is the usual cause.
  • Nothing is exported. Read the verdict: a failure is a refusal, not a glitch. The plain line under the score names the next step.
  • The push button is off. The plan has to be a pass (or one you deliberately accepted), and the mission on screen has to be the one that was solved. The Run tab says which of those it is.
  • No hub answers the scan. Turn the hub on, close Pybricks Code (it holds the connection), and scan again.
  • The port is busy. The studio takes the next free one and says which.
