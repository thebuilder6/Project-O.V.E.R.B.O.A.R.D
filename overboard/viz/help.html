OVERBOARD Studio

Time-optimal mission planner for a LEGO differential-drive robot. It plans the motion, checks it against a reachability model, and only then lets a trajectory leave the machine.

The loop

  1. Mission - name it, and give it a start pose and waypoints. Click the field to add one; drag to move it. A waypoint can be marked stop (the robot halts there) and/or carry a heading.
  2. Robot - the machine's limits: wheel size, mass, motor, gear ratio, force, slip. The shipped example is a placeholder; measure yours (see Calibration below) before you trust a plan.
  3. Solve - picks the planner's candidates, solves each with CasADi/IPOPT, and validates. Solve in the header starts it.
  4. Result - the verdict, every candidate with its numbers, the envelope, and the downloads. Run pushes to the hub.

What a verdict means

VerdictReading
PassedEvery candidate gate held: envelope, tracking, force, slip. This is the only verdict that can be pushed to the robot.
FailedNothing is exported. The message names the failing segment and the excess. With best effort on, a plan that only misses the accuracy budget is written and marked unapproved; a force, slip or convergence failure never is.
UnvalidatedThe solve ran without the validator. The trajectory exists, the push stays off.

A pass is a model prediction, not a measurement. The validator is not yet a full digital twin: motor, odometry and slip are modelled only in part. Treat the envelope as a budget, and check the first runs by hand.

Where your files are

Missions, calibration and generated firmware are kept outside the program, so an update never touches them. OVERBOARD_HOME points the whole folder somewhere else.

SystemFolder
Windows%LOCALAPPDATA%\OVERBOARD
macOS~/Library/Application Support/OVERBOARD
Linux~/.local/share/OVERBOARD
  • missions/ - saved missions, one JSON each, under version control.
  • calibration/ - the SysId session, the sheet, the fit and the digital twin.
  • pybricks_code/ - the firmware, including the generated hub_mission.py and your robot_config.py.
  • mats/ - the field artwork, downloaded on request.
  • docs/ - every document from the project, including the calibration procedure and the design notes.

A trajectory is written into the folder of the solve that produced it, and is listed with the other artifacts under Result.

Calibration

The SysId loop measures the real robot and writes the numbers the planner needs: collect a session over Bluetooth, run the reference tests when the hub asks, fill in the sheet, fit, then compare against the digital twin. Until that is done the envelope describes the example robot, not yours. docs/CALIBRATION_PROCEDURE.md walks through it.

Pushing to the robot

Run imports the trajectory and pushes hub_runner.py with pybricksdev. It needs the robot connected over Bluetooth or USB, and it refuses a trajectory that is not a pass, or a mission that changed after the solve. The hub reports its own odometry back, which the studio compares with the plan.

Command line

The same program without the browser. Every option the studio sets has a flag:

overboard -w mission.json -o out.traj --validate
overboard --doctor
overboard --gui

--doctor prints the Python, the packages, the example files, the folders and the ports, with the command that fixes anything missing. Run it first when something does not work.

If something goes wrong

  • The solve never finishes. Cancel, cut the sample count under Solve, or use the fast preset; a long mission with many candidates is the usual cause.
  • Nothing is exported. Read the verdict: a failure is a refusal, not a glitch. The named lever - a wider accuracy limit, one more candidate, another propagation model - is the thing to change.
  • The push button is off. The trajectory has to be a pass, and the mission on screen has to be the one that was solved.
  • The port is busy. The studio takes the next free one and says which.
