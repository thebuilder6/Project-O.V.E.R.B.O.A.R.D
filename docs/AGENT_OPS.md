## Install and environment

- Install the core path: `pip install -r requirements.txt` (solver and studio). `--validate` and `--push-hub` also need `pip install -r requirements-optional.txt` (jax, immrax, pybricksdev; verified with JAX 0.6.2 and pybricksdev 2.3.2; a fresh install brings JAX 0.12.0 and Immrax 0.3.8, which need numpy 2.2, so requirements.txt asks for numpy below 3.0 and not below 2.0).

- The one-click path for a new user: `install.bat` (Windows) or `sh install.sh` (macOS/Linux) creates `.venv`, installs the core and the optional packages and runs the check. `start_studio.bat` / `sh start_studio.sh` start the studio with that `.venv`, and install it first when it is not there. `overboard/main.py` reports the install command instead of an ImportError when the core packages are missing, so `--doctor` works on a clean machine. The `.bat` files must keep CRLF line endings: `cmd.exe` cannot find a batch label in a file with LF endings, and `install.bat` calls a subroutine. `.gitattributes` keeps them out of the line-ending conversion so the CRLF survives into a ZIP download; the `.sh` files must stay LF.

- `python -m overboard.main --doctor` reports the Python version, every package, the example files, the output directory and the ports, with the install command for anything missing. It is the first thing to run when something does not work.

## Solve options and the candidate set

- The 3-Pillar Unified Trajectory Engine is the **only planner**; the CasADi/IPOPT optimizer is the backend it drives. `--no-unified` and `--simple` are **removed and rejected** as unknown options. The old Multi-Verse pipeline has been removed - it is in the git tag `archive/legacy-2026-10` - and has no CLI entry point. Do not use `--workers`/`--no-parallel` as a quality claim.

- The candidate set is the planner's: three frontier candidates (`frontier_sprint`, `frontier_sweeper`, `frontier_exploratory`), all per-segment, all with the discretisation metric and the linear epigraph force bounds. `--candidates N` (default 2) says how many of them are solved. The per-segment timing model is the only model: every segment gets its own `dt_i`, and it is held to the wheel-jerk discipline (KI-022). The retired equal-duration comparison is kept in `docs/HEURISTICS_AND_VERIFICATION.md`. A waypoint is a legitimate timing boundary only when the robot stops there AND the heading is pinned: everywhere else the pieces must stay linked, and the per-segment model requires the wheel acceleration - and so the wheel force - to be continuous through the point (KI-024). The CPU audit runs per candidate, so a partial pass cannot block a later fully passing candidate. Do not force a mode silently. **When a run produces nothing usable - no candidate passes the gates, or (without validation) none converged - the CLI tries the other seeds as a rescue before giving up** (KI-048): the planner's three candidates are all of the same frontier family, so without the rescue a path that beats them ends with no trajectory at all. The rescue uses the per-segment model on a validated run (that is where the measured rescues came from) and the same model on an unvalidated one; a rescue candidate is only selected when the candidate set itself produced nothing that passed. It costs nothing when the plan works, and one parallel round of solves when it does not.

- `--fast-polish` uses the fast solve path: the warm-start IPOPT pass gets an iteration budget (200) and, if it runs out, the mission is solved cold from that iterate (KI-047). A mission that converges inside the budget returns a bit-identical trajectory. Measured on the 10-waypoint complex mission (2026-10-21, the pre-widened example ranges): the plain warm pass is 1257 iterations and 6.087 s in 33 s, `--fast-polish` is 200 + 233 = 433 iterations and 6.096 s in 12.5 s - 2.9x fewer iterations and 2.6x less wall time for a trajectory 0.14% slower. Cold-starting from the original guess is faster still but lands at 8.67 s, which is why the cold stage keeps the warm iterate. A mission where the cold finish fails falls back to the unbudgeted pass, so nothing that solves today stops solving. Off by default; do not enable it silently.

- The candidates are independent, so `--validate` with `--candidates N` solves them in worker processes (`--workers`, `--no-parallel` keeps them in this process) and then scores them one by one here, where the JAX validator is warm. The trajectories are identical to the sequential run. A patched or injected optimizer stays sequential: a worker cannot import it.

- `--sweep` is **removed and rejected** as an unknown option (the retired timing-mode x accuracy-weight grid; the 80 ms invariant mesh had removed the need for it). The measurements it produced are kept in the whitepaper's research record.

- `--force-weight` (off by default) adds a **third objective term** to the NLP: the time integral of the squared wheel-force utilisation, against both the stall force and the per-wheel traction limit. The hard per-wheel limits still apply; the term *prices* the force instead of only constraining it, so a plan that runs near the traction limit is paid for before the gate rejects it. The weight is 0 by default, so the objective is duration plus jerk unless the operator asks for more.

- The optimizer also takes three parameters the command line does not expose yet: `cost_metric` (`"jerk"`, the default, or `"discretization"`, which prices the three mismatches the 5 mm tracking gate actually measures - the chord against the arc, the heading rule against the reference's, and the 20 ms command hold - instead of the wheel jerk), `epigraph_constraints` (the force bound as four linear inequalities instead of a `sqrt` with a 10⁶ Hessian spike, which is the same limit written smoothly), and `sample_weights` (a per-sample weight on the smoothness or discretisation term, so a mission can say *where* it wants the plan accurate). The CLI has only `--force-weight`; the other two are library parameters, and `TrajectoryOptimizer.solve` is where they are read. The unified planner selects `cost_metric="discretization"` and `epigraph_constraints=True` for its own candidates.

- `--polish` (off by default, needs JAX) runs the **post-solve gradient polish** (`UnifiedPathEngine.gradient_polish` in `overboard/core/unified_planner.py`): the reachability rollout is differentiable, so the engine is differentiated through and the gradient says which sample states move the reachable set most. The plan is then re-solved, warm-started from the one that was found, with those samples weighted. The engine does the same on its own when its champion rides within 10 % of the tracking gate (`polish_candidate_sensitivities`, called from `plan()`), so a plan that nearly misses the gate gets one self-healing pass. A polished plan is kept only when it is **not slower** and not worse in the reachability: the planner is time-optimal, and a pass that trades time for a smaller tube inverts the objective.

- The **3-Pillar Unified Trajectory Engine** (`overboard/core/unified_planner.py`) is the only planner: it allocates the 80 ms invariant mesh ($\ge 10$ nodes/segment on curved apexes), generates the three candidates (`frontier_sprint`, `frontier_sweeper`, `frontier_exploratory`) with the Kinetic Frontier analytical seed generator in a few milliseconds, and solves with discretization-consistent collocation and linear epigraph force bounds. `--candidates` only truncates the three. `--unified` and `--no-unified` are removed and rejected. **It is not a certification claim**: whether a given mission passes is decided by the gates, and the measured pass/fail ledger is in `docs/HEURISTICS_AND_VERIFICATION.md`. The GA comparison it used to quote (5.365 s against the 44-gene champion's 5.417 s) predates the narrowed test ranges and is kept in the whitepaper's research record, not here.

- `--preset fast|balanced|safe` fills in options the user did not set: fast = 1 candidate without validation, balanced = the defaults, safe = 3 candidates, `--validate`, `--propagation tick` and a controller export. Explicit flags always win. `safe` uses the closed-loop model because the example config's widened ranges no longer fit an open-loop tube on a curved path (KI-049/KI-050).

## Validation, selection and the propagation model

- `--validate` gates every output and the exit code. It requires JAX/Immrax. With `--candidates N` (default 2), `overboard/main.py` solves N of the planner's three frontier candidates and validates each. It selects a passing one: the **fastest**, with the envelope breaking a duration tie. The **5-part path fitness score** (the reachability spread at the stops, the slip risk, the RMS wheel force, the tracking error and the run time) is reported for every candidate, so the rule can be re-run offline, but it does not decide. A candidate that failed a gate is never chosen, however fast it is. `tests/test_regressions.py` pins the rule. Without `--validate`, only the first candidate (`frontier_sprint`) is solved. If validation fails, no `.traj`, controller, Python file, or `_stats.json` is written.

- `--propagation [plant|tick]` chooses the reachability model the envelope gate uses (KI-049, KI-050). "plant" is the default: the plant is embedded and propagated, and the controller is evaluated *outside* the propagation, at the tube's midpoint, so the tube bounds an open-loop plant driven by a pre-recorded command. "tick" embeds one 20 ms tick of the closed loop (controller, pose estimate and delayed command inside the map) and propagates that, so the map's Jacobian carries the feedback term and the tube contracts the way the robot's does. It needs a Jacobian inclusion (the natural extension explodes) and costs 2-3x (`jac`) to 7-10x (`mjac`) the validation time. The propagation and the inclusion functions are in every candidate of the `##OVERBOARD-VALIDATION##` line, so an envelope is never read without the model that produced it. `research/harness.py` takes the same flag. Measured on the six example missions (`git show archive/research-2026-10:docs/measurements/2026-10-20-tick/`): the tick tube is uniformly tighter - 2.9x on the S-curve, 3.2x on the stops, 4.4x on the complex mission - and the tracking error is identical to the last digit, so **no verdict changes**: four missions pass and two fail under both, and the two that fail fail on the tracking gate, which is the discretisation mismatch, not the envelope. The default stays on "plant": the tick map's own gain is on the paths where the plant propagation *diverges* rather than merely widens (a calibrated robot: the S-curve's plant tube is cut off at the 50 mm guard, 53.6 mm against the tick map's 18.8 mm), and with the digital twin it is wider still (12.1 cm against 5.1 cm), which is the conservative direction and not a hazard.

- With `--validate`, `overboard/main.py` prints one machine-readable line per run: `##OVERBOARD-VALIDATION## {json}` with the per-candidate and per-segment envelope, limit, drift and reasons, and the run-wide `envelope_limit_m` the gate applied (KI-054). Every candidate also carries its **score vector** - `duration_s`, `envelope_cm`, `tracking_cm`, `max_excess_cm` (the biggest excess of the envelope over the local limit; negative means margin), `peak_jerk_m_s3` and the **fitness score** with its parts (`fitness_s`, `stop_spread_cm`, `slip_risk`, `rms_force_n`, `rms_force_util`) - so the selection rule can be re-run offline without solving again. The studio parses it to show which part of the path failed. Nothing is written to disk on a failed validation, so the report goes to stdout, not to a file - except with `--best-effort`, which writes the best candidate whose only failure is an accuracy excess (envelope or tracking) and marks it `validation: {passed: false, best_effort: true, ...}` in the `.traj` root and the `_stats.json`. The payload then carries `"best_effort": true` too, so the studio says "failed, shown" instead of "not checked". Keep the JSON valid (`Infinity` breaks `JSON.parse`).

## Export, the hub and the SysId commands

- `--validate --export-format controller` writes `<output>_controller.json`; `--export-format python` writes `<output>.py` (legacy list format); `--export-format python-compact` writes a packed module for `ramsete_compact.py`/`ramsete_compact_events.py`; `--benchmark` writes `<output>_stats.json` after the export gate.

- `--push-hub` pushes the trajectory to a Pybricks hub and runs it there, without the Pybricks IDE. It writes the packed trajectory to `pybricks_code/hub_mission.py` and pushes `pybricks_code/hub_runner.py`; pybricksdev bundles the local imports, so `robot_config`, `ramsete_compact_events`, `ramsete` and `hub_mission` travel with it. `--hub-conn ble|usb` picks the transport (BLE needs no driver; USB needs a WinUSB driver on Windows), `--hub-name` picks the hub, `--hub-log` saves the hub console output. The runner prints the measured pose as `POSE,x_m,y_m,heading_deg` and every exported event as `EVENT,name`. It needs `pybricksdev`; a plain solve never imports it.

- The hub over Bluetooth is found by **probing what is nearby**, the way the Pybricks IDE finds it (`hub_ble.py`): Windows does not report the advertised Pybricks service UUID and the local name in the shape `pybricksdev`'s filter wants, so the advertisement alone does not identify a hub (KI-033). `python -m overboard.deploy.hub_deploy --list-hubs` is the IDE's device picker: it shows what the adapter can see and says which device is the hub. The CLI, `--push-hub`, `python -m overboard.sysid.collect` and the studio's push all go through it.

- `python -m overboard.deploy.hub_deploy <script.py> [--conn ble|usb] [--name NAME] [--out session.csv]` pushes any script to a hub and saves its console output, without solving anything. Use it to run the hub menu (`pybricks_code/robot.py`) or the sysid logger (`pybricks_code/sysid_digital_twin.py`) and capture the session that `python -m overboard.sysid.fit` reads. `--out` is written as the output arrives, so a dropped Bluetooth link costs the last test instead of the whole session. `--list-hubs` pushes nothing: it lists the Bluetooth devices around and says which one is the hub.

- `python -m overboard.sysid.collect --conn ble --profile examples/drivebase_profile.example.json` collects a SysId session from the hub and fits it in one command: it pushes `pybricks_code/sysid_digital_twin.py`, captures the session as it arrives, converts the hub's `POSE` lines to `hub_poses.csv`, and writes `sysid_fit.json`. The operator still presses the hub button between tests. A dropped Bluetooth link does not lose the run: the session is written as it arrives, so what arrived is fitted. The poses are the hub's own odometry, so the distance scale, the heading scale and the brake slip carry no information and stay at their defaults; replace `hub_poses.csv` with tape measurements and re-run `python -m overboard.sysid.fit` to calibrate them. The actuator part of the fit (gain, time constant, delay, backlash) needs no measurement and is calibrated either way. `--profile` is optional: only the fit needs the wheel radius, so the collect works without it and the command then says what to do next. `--sheet <path>` writes the measurement sheet after the collect: the CSV the fitter reads and a browser form next to it.

- The hub-to-host contract is the session format: `TEST_START <name>`, `META,key,value` (comma separated, so `META,run_id` identifies the test), `DATA`, a `t_ms,...` header, rows, `TEST_END,<n>`. A test reports its pose with `POSE,x_m,y_m,heading_deg` and an event with `EVENT,name`; `overboard.sysid.fit.poses_from_hub_session` turns the pose lines into the pose-CSV rows (`run_id,stop,x_m,y_m,heading_deg`) the fitter and the comparator read, and a pose takes the run id of the test that was open when it was printed. The heading is counter-clockwise positive, the same convention as the planned trajectory, while the hub's `drivebase.angle()` is clockwise positive, so the fit flips one of the two when it divides them.

## The browser studio

- Browser studio: `python -m overboard.main --gui` (port 8000, `--gui-port` to change it). It serves `overboard/viz/studio.html` from `overboard/gui_server.py`, runs the CLI in a subprocess, and never bypasses the export gate. The page is three columns: the left one is what you set, the canvas is the work, the right one is what you read. Both side columns are tabbed - the left has Mission, Robot, Field and Solve, the right has Result, Waypoint, Plots and Run - and every tab strip is wired by the one controller in `overboard/viz/studio.js` (`setupTabs`), so a new tab is a `role="tab"` button and a `role="tabpanel"` section and nothing else. The header's status line always carries the result (`3.70 s | 1.23 m - validated`), so a tabbed column cannot hide the answer, and a solve or a failure brings the Result tab forward by itself. Three registries carry the parts that grow: `PLOTS` (a plot is one entry; the tab strip and the drawing both come from it), `CANVAS_LEGEND` (the key to the field's colours, so it cannot go stale) and the tab controller. `docs/STUDIO_UI_INVENTORY.md` lists every control and the structure, and `tests/test_studio_inventory.py` checks the document against the page. The studio leaves the backend at the CLI default and forwards neither `--unified` nor `--self-consistent`; there is no planner toggle and no timing-mode or collocation switch. `overboard/viz/studio.js` holds the mission editor: undo/redo history, the browser session in `localStorage`, the field canvas, the per-segment validation table, the robot config editor, the path-length readout, the fast-polish switch, the stop/event badges and the candidate explainer. The field canvas takes the operator's own mat image (FIRST's artwork is not ours to ship) and draws the earlier solves as faint paths, so a new trajectory can be compared with the ones before it. The field block also picks the **season**: the mission models standing on the mat come from `fields/<season>.json`, measured off FIRST's public field wireframe, and the mat's picture is still the operator's own file. The server owns the collision maths (`overboard/viz/fields.py`): after a solve it reports where the planned path ran into a mission model, and the studio marks those places on the canvas and lists them under the result. Nothing is blocked or planned around - the collisions are only marked, and a collision shallower than the field's placement uncertainty (50 mm, because two independent readings of the same wireframe disagree by up to 100 mm) is reported as uncertain rather than as a hit. The provenance is in `research/field_maps/README.md`.  The field block offers every field in `fields/`: ours (the footprints of the models built from real parts) and RoboVibe's (the scoring areas, which cover more of the field and are read with the anchor as the corner of a shape, turned clockwise about it - with that reading the two agree to a few millimetres). `research/field_maps/convert_robovibe.py` makes RoboVibe's field file from the YAML read out of their public bundle. The studio can fetch the season's mat picture with **Download the mat**: FIRST's mat artwork is copyrighted, so it is not in the tree - the server downloads it on request from the URL the field file records (pinned to a commit) and keeps it in `mats/`, which is not tracked. The mat's size comes from the field file, so the picture and the footprints share one frame. `viz/studio.css` is local, so the studio works offline. It is the only browser UI: the WebSocket live view (`live_visualizer.py`, `viz/index.html`) was removed, and the CLI has no wrapper for the studio any more - `--gui` opens it, and the mission and the solve are driven from the browser.

- The studio passes `--fast-polish` when its switch is on. It is off by default, like the CLI flag. The position rule is unconditional, so the studio has no self-consistent switch to pass.

- When a validation fails, the studio names the lever that might fix it - the closed-loop tick propagation, the gradient polish, the soft force weight, or a smaller accuracy weight - and each is a button that re-solves. The candidates come from the validation report, which carries the accuracy weight of each candidate so the leaderboard is readable.

- The studio draws the command line's plots from the samples it already has: the velocity profiles, the wheel forces against the validator's force limit, the accelerations, the heading, and the convergence. The limits come from the server (`RobotConfig.get_max_force_at_velocity_robust`), and the convergence needs `overboard/main.py --iteration-history PATH`, which writes the solver's first guess and its solution; the first guess is drawn on the field as a dashed path.

- The studio keeps a calibrated model with the robot: `POST /api/robot/model/load` reads a `sysid_fit.json` into `calibration/<robot>.sysid_fit.json`, and every solve then passes `--sysid-fit` (which turns validation on, because the fitted plant is only used by the validator). The gain interval is the band the validator plans against. A 1 % gain band is 10 mm of position error over a 1 m path, but the controller corrects that speed error, so it barely moves the tracking error - it widens the *envelope* instead (11.8 mm on a 1 m straight, against a 20 mm threshold). A measured model therefore makes most paths fail on the envelope gate, not the tracking gate. On a *curve* the tube still crosses the validator's 50 mm guard, but that is **not** the reachable set being wide: on the S-curve the sampled reachable set is 4.09 mm against a 48 mm tube, because the validator propagates the plant open-loop and the feedback contraction is not in the tube. See `docs/research/RQ-A_tracking_error.md` findings F5 and F12, and KI-049.

- A pushed run is compared with the plan in the studio: the server builds the report with `overboard.sysid.compare.compare`, after putting the hub's pose into the plan's frame (the hub's odometry origin is where the robot sat, which is the plan's first waypoint, so the pose is rotated by the plan's first heading and moved by its first position).

- The studio can push an approved trajectory to a hub: `POST /api/push` runs `python -m overboard.deploy.hub_deploy --trajectory <the solved .traj>` as a subprocess, so the export gate still holds (a failed solve has no trajectory to push). The push button is also gated on the *validator's* verdict, not on the switch on the Solve tab: a trajectory that was never validated is not an approved one, so the button stays off and the Run tab says so. The hub's console streams into the job log, the `POSE`/`EVENT` lines become the measured marker on the canvas, and the session is written to `missions/<name>.session.csv`. The robot's own files are read as text (`MISSION_EVENTS`, `WHEEL_DIAMETER_MM`, `AXLE_TRACK_MM`) because `pybricks_code/` is firmware and cannot be imported on the host.

- The studio can run the whole calibration: `POST /api/calibration/collect` pushes `pybricks_code/sysid_digital_twin.py` and captures the session, `GET`/`POST /api/calibration/sheet` reads and writes the measurement sheet as a form, and `POST /api/calibration/fit` fits the model from the session and the sheet. The files live in `calibration/<robot>.{session.csv,sheet.csv,poses.csv,sysid_fit.json}`. The fit takes the wheel radius from the session's own `META,wheel_diameter_mm`, so no drivebase profile file is needed. The fitter needs all three numbers of a row: a test that does not turn has a turn of zero.

- `docs/CALIBRATION_STUDIO_PLAN.md` is the design for the sysid loop in the studio: the measured model belongs to the robot, a pushed session can be compared but not fitted (its poses are the robot's own odometry), and the measurement sheet becomes a form. All four phases are built.

- `docs/STUDIO_HUB_PLAN.md` is the design for the studio's push-to-hub feature. All four phases (the push, the result overlay, the robot-file checks and the sysid compare/fit loop) are implemented. The push has never run against a real hub: the tests use a stand-in for the hub client.

- docs/STUDIO_3D_SIMULATOR_PLAN.md is the design for the far stretch goal: a client-side 3D WebGL (Three.js + Rapier3D Wasm) physics simulation tab in the studio with clustered LEGO mission models and articulated interactable mechanisms.

- `docs/STUDIO_UI_INVENTORY.md` lists every control, readout and generated region in the studio, panel by panel, with the counts (76 controls with an id, 150 ids in the page) and the problems a redesign has to deal with. Read it before changing the studio's markup or adding a control, and keep it in step with the page.

- The missions folder is its own git repository: the studio commits every save, lists the history and can restore an earlier version. The commits are made with a fixed identity, so no git configuration is needed on the machine, and the project repository is never touched.

- The studio's undo covers the robot config as well as the mission, and the arrow keys nudge the selected waypoint (1 cm, Shift 10 cm, Alt 1 mm). A held key is one undo step.

- The studio writes a **one-page mission report**: `overboard/viz/report.js` builds a self-contained printable document from the numbers the Result tab shows, the browser posts it to `POST /api/jobs/<id>/report`, and the server writes it next to the trajectory as `<name>_report.html` (`GET /api/jobs/<id>/report` serves it as a page). It is built from the studio's own numbers, so it cannot disagree with the screen. The report fits one A4 page for a typical mission.

- The studio also writes a **one-file project**: `format: overboard-project`, `version: 1`, holding the mission, the robot config, the solve options, the measured model and the field. **Download project** saves it and **Open project...** brings all of it back; a file that is not a project is refused with a reason rather than half-read.

- The studio runs one solve at a time. A second tab, or a reload during a solve, attaches to the running job (`GET /api/jobs/current`) instead of starting another one.

## Research and benchmark tooling

- Stress run: `python research/suite.py --count N --seed S --out DIR` writes random missions; `research/robots.py` draws random robots (the constants move, and every declared range moves with its constant, so a drawn robot is still one the ranges describe). `python research/harness.py --missions DIR --out FILE --specs default --robot-jitter 1 --robots 2` plans each mission for each robot and scores it with the production gates; each record carries the robot's factors, so `python research/analyze.py errors|robots FILE` reads it back. Measure against a pinned tree (`OVERBOARD_TREE`) when the working tree is being edited. The run of 2026-10-20 is in `git show archive/research-2026-10:docs/measurements/2026-10-20-stress/`: on random paths the **gates**, not the planner, are the binding constraint (92 % of the failures are the forward-integration and tracking gates, which are one discretisation artefact - the self-consistent rule removed every integration failure in the set at the time), and the robot's own constants decide the verdict on 2 of 45 missions.

- Benchmarks: `python benchmark.py --mode pipeline` (also `cli`/`random`/`solver`; the default config is `examples/fll_choreo.json`). All four modes work (KI-015): the pipeline mode prints `FAILED` for a solve that did not converge, and the random mode validates against the config it actually used. `--mode solver` solves every example mission and reports the wall time, the IPOPT iteration count and the trajectory duration; add `--fast-polish` for the fast path. It is the reference table for any solver change.

## Calibration and the digital-twin fit

- `docs/CALIBRATION_PROCEDURE.md` is the human procedure for calibrating a drivebase: what to set up, what to measure, and the commands to run. The operator drives the robot through the collector tests and measures the end pose of the five that need a tape (`odometry_straight`, `odometry_turn_cw`, `multi_stop` at three stops, `brake_from_300`, `brake_from_600`). The measurements go in a sheet keyed by test name and repeat, never by run id, so the order the tests ran in does not matter.

- The calibration-critical tests run three times each (`REPEATS` in `pybricks_code/sysid_digital_twin.py`) and the collector says which repeat a run is in with `META,repeat`. The step order is reversed on every other repeat, so a drift over the run cannot land on the step index. The fit groups the runs by repeat and reports a 95% t-interval per parameter in `<name>_between_runs` and `<name>_ci95`; with a single run there is no interval. `digital_twin.py` uses `gain_ci95` as the validator's gain band when the fit has one, and falls back to the observed min/max when it does not. The interval covers the run-to-run variation and any drift over the session, but not the error of the tape measure, which is systematic and never averages out.

- The fit measures two things the robot config could only declare, and both are inert without a fit. `drift.drift_deg_per_m` is how much the robot curves per metre when told to drive straight: the plant adds `drift_rad_per_m * v` to the heading rate, because the plan's straight segments are straight and 1 deg/m is 8.7 mm of lateral error per metre. It is a **slope, not a subtraction**: the step tests drive straight at five speeds, so the heading rate against the speed is a line whose slope is the drift and whose intercept is the gyro's bias, and a bias cannot leak into a slope the way it leaks into a subtracted one. The tape's lateral offset is an independent estimate, and the fit reports the disagreement. `stall_torque.t_max_nm` is the motor's stall torque, measured by pushing into a wall; the fit hands it to the robot config, which is where the motor lives, so the validator does not keep a second limit of its own. The motor is measured on both ends and every tool uses the measured pair: the collector's `top_speed` test lifts the robot so the motor runs free and measures the speed at which it makes no torque, the fit rejects that number when the robot reached the commanded speed instead (then the command was the limit, not the motor), and `main.py --sysid-fit` writes the measured stall torque and no-load speed into the robot config, so the optimizer, the CPU audit, the validator and the exported controller all plan against the same motor (KI-010). The model is in `overboard/models/drivetrain.py` and `docs/research/RQ-B_drivetrain_model.md` has the cross-check against an independent simulator.

- The step fit is a two-stage search. The first pass is a blind grid over the whole plausible range, so a local minimum cannot fool it. The second pass refines around that answer at a millisecond, and the two amplitudes of the model are solved in closed form because the model is linear in them, which also gives the covariance. The first pass alone could only land on a 10 ms boundary, and that quantisation was a floor on the reported time constant and delay.

- The wall is a reference for the distance scale that does not move and does not have to be read by hand. The `wall_homing` collector test drives the robot slowly forward from a marked start and stops when the wheels are blocked, so the distance it covered is the distance to the wall; the host turns that into the same scale the tape gives, as `distance_scale_homing`, and reports the wall and the tape side by side with their disagreement. The wall distance comes from the drivebase profile's `wall.distance_m`, measured to where the robot's centre rests against the wall, so the bumper's offset never enters. A run that never reached the wall is rejected: the robot has to be blocked while it is still commanded, which is the last row that has a command on, not the settle row the collector writes afterwards. The approach may be crooked, because the distance to a wall changes with the angle only to the second order, but the wall does not straighten the robot, so the wall cannot measure the heading and the drift still comes from the speed regression. That regression needs three points: a line through two has no degrees of freedom, and numpy refuses to scale its covariance.

- `python -m overboard.sysid.fit <session.csv> --write-sheet calibration_sheet.csv` writes the blank sheet for the tests in a session: one row per measurement the session needs, with the test name, repeat and stop filled in. `python -m overboard.sysid.fit <session.csv> --from-sheet calibration_sheet.csv --out-poses poses.csv` turns the operator's sheet into the measured-pose CSV, looking each test and repeat up in the session, converting millimetres to metres and flipping the turn (the sheet counts a turn to the right, the trajectory counts a turn to the left). It reports a row for a test that did not run and a measurement that is missing. The collector says how many poses each test needs in `META,poses`.

- `python -m overboard.sysid.fit <session.csv> --sheet calibration_sheet.csv --profile my_drivebase.json --out sysid_fit.json` fits straight from the operator's sheet, so there is no intermediate pose CSV: the same lookup and the same warnings, one command. `python -m overboard.sysid.fit <session.csv> --write-form calibration_sheet.html` writes the sheet as a self-contained form in a browser (`overboard/sysid/sheet_form.py`): one number input per measurement, the measurement convention at the top, a count of what is still missing, and a **Download CSV** button that writes the file the fitter reads. The form also takes a sheet saved earlier, so a session measured in two goes is not measured twice. It is one file with no server, so it works offline; the studio has its own version of the same form, on the server (`overboard/gui_server.py`).

- Digital-twin fit: `python -m overboard.sysid.fit <session.csv> --poses <poses.csv> --profile examples/drivebase_profile.example.json --out sysid_fit.json`. Logs come from running `pybricks_code/sysid_digital_twin.py` on the Hub; no hardware logs are checked in. Compare planned and measured poses with `python -m overboard.sysid.compare output.traj poses.csv --run-id <id>`.

## Planner internals and the controller

- The reference interpolates the heading, the speed, the turn rate and the Ramsete gain as independent lines, but they are coupled: the turn rate must be the derivative of the heading, and the gain must be `sqrt(w^2 + b*v^2)` of the interpolated values. The turn rate is now the derivative of the interpolated heading, in `ramsete_compact_events.py`, `ramsete_compact.py`, `ramsete_fast.py`, `ramsete.py` and `immrax_validator.py` together, so the model and the robot stay in parity (KI-027). The model takes the heading difference the short way, exactly as the firmware does, so the two agree even above 180 degrees per sample interval. Deriving the turn rate from the interpolated heading instead is worth 2-3.6x on the tracking error and turns five of the nine failing (mission, density) cells into passes; the gain inconsistency is worth nothing. See `docs/research/RQ-A_tracking_error.md` finding F7 and Fix 3.

- The gear backlash is a position uncertainty, not a velocity offset: it widens the reachable set by `backlash/2 * t` and must never be subtracted from the commanded wheel speed (KI-025). The tracking metric is position-only; the heading error is reported as `max_heading_error_rad` but is not gated, because the heading behaviour is not calibrated yet.

- The validator models the controller that **runs**, not a legacy one: `ramsete_compact.py`, `ramsete_compact_events.py` (the pushed-run entry point) and `ramsete.py` all run a synced 20 ms heartbeat, pass floats to `drive()` without rounding, and take the turn rate as the derivative of the interpolated heading (KI-027, KI-028). `immrax_validator.py` mirrors all of that, because the wheel-force hold error is proportional to the hold and the tracking gate is decided on it. **There is now one implementation of the controller in the firmware**: `ramsete.py` holds the odometry, the Ramsete maths and the loop, `ramsete_fast.py` delegates to it, and `ramsete_compact.py` delegates to `ramsete_compact_events.py` with the events off - so a second copy of the controller can no longer drift away from the one that runs. `tests/test_firmware_events.py::TestFirmwareParity` pins the parity. The firmware's `KinematicLimiter` now uses the **per-wheel** traction limit with the lateral weight transfer - the same `nl = mg/2 - m*h*a_c/b` the host's `wheel_normal_forces` computes (KI-010) - and its fallback numbers are the robot's own (mass 1.5 kg, 19.4 rad/s, 0.138 Nm, `cof` 0.6, `h_cg` 0.05 m), so an empty config does not silently plan a weaker robot. The backlash is no longer applied there at all: it is a position uncertainty in the reachability envelope (KI-025), and the limiter only enforces the torque and traction limits.

- The validator has two **propagations** (`overboard/verification/immrax_validator.py`, `PROPAGATION`). "plant" is the default: the plant is embedded and propagated and the controller is evaluated *outside* the propagation, at the tube's midpoint, with the command held for the tick - so the interval arithmetic never sees the feedback, and what it bounds is the reachable set of an open-loop plant driven by a pre-recorded command. "tick" embeds one 20 ms tick of the **closed loop** as a discrete map (`ClosedLoopTickMap`), with the controller, the robot's own pose estimate and the delayed command inside the map, and propagates the map once per tick: the map's Jacobian then carries the feedback term `dF/dx = dPhi/dx + (dPhi/du)(dN/dx)` and the tube contracts the way the robot's does. On the shipped S-curve with a +/-1 % gain band the plant propagation is cut off at the 50 mm guard (53.6 mm) and the tick map with the mixed-Jacobian gives 18.8 mm, which passes the 20 mm gate, and both contain the sampled reachable set (`git show archive/research-2026-10:docs/research/rq_a/exp20_closed_loop_tick.py`, KI-049). It needs a Jacobian inclusion - with the natural extension the closed-loop map explodes (627 mm) - and it costs 2-3x (`jac`) to 7-10x (`mjac`) the validation time, which is why it is opt-in. On the default plant it is a clear win - with the mixed-Jacobian the S-curve, the stops and the complex mission stop diverging and pass the 20 mm gate (1.88, 1.30 and 1.83 cm against 5.36, 5.31 and 5.07 cm), and every tube contains the sampled reachable set (`git show archive/research-2026-10:docs/research/rq_a/exp22_twin_propagation.py`). With the **digital twin it is worse** (5.8-12.1 cm against 5.1 cm), and the reason is the twin's *plant state*: the two wheel speeds are interval coordinates whose spread feeds the command, and the interval arithmetic counts that growth twice. It is **not** the robot's pose estimate - the control that drops the estimate is not smaller and is unsound (`git show archive/research-2026-10:docs/research/rq_a/exp23_twin_tick_belief.py`) - and carrying the estimate's *error* instead was measured and is worse too. That is why the default stays "plant".

- The propagation is now reachable from the command line: `overboard/main.py --propagation [plant|tick]` and `research/harness.py --propagation`, and every candidate in the `##OVERBOARD-VALIDATION##` line carries the `propagation` and the `inclusion` functions (KI-050). Two rules come with it. **The controller must not unpack the pose:** `x, y, theta = current_pose` is the JAX `unstack` primitive, Immrax's natural inclusion has no rule for it, and the tick map dies with "unstack not in inclusion_registry" - so the pose is read by indexing, which compiles to slice+squeeze and gives the same number. And **an envelope is never read without its model**: the report, the studio's validation note and the studio's chip tooltip all name the propagation, the same rule as `envelope_truncated`.

- The position rule is self-consistent and unconditional: it integrates the interval's velocity along the integrated heading with a four-node Gauss-Legendre rule, so the samples lie on the path the plan's own (v, omega) profile traces and the headings are its tangents (KI-026). The trapezoidal branch and its `--self-consistent`/`--no-self-consistent` switch were removed. The tracking error roughly halves on the curved missions: the S-curve goes from 1.31 cm to 0.55 cm (still 0.05 cm over the gate) and the events mission goes from failing both candidates to passing both (0.32 cm and 0.40 cm). The complex mission's passing candidate moves from 0.49 cm to 0.51 cm and now fails by 0.01 cm, and the stops mission gets slower. **It is the only rule now**: the switch that restored the trapezoidal rule was removed (KI-051, KI-052). The candidate set and the seed conclusions were re-measured under it. The collocation and what it costs are written up in `docs/HEURISTICS_AND_VERIFICATION.md` §5.7.

- The **sample count follows the path**. `TrajectoryOptimizer.get_segment_sample_counts` splits the sample budget (`segments * samples_per_segment`) across the waypoint segments **in proportion to their arc length**, with at least three samples each, so a long segment is sampled finely and a short one coarsely. The total is unchanged (`N = 1 + sum(s_i)`), but the sample-to-waypoint mapping is no longer `k * samples_per_segment`: the code carries a `waypoint_sample_indices` table, and `stats["segment_samples"]` reports the counts, so a reader can map a sample back to its waypoint. The objective follows the layout - the duration term is `sum_i(s_i * dt_i)` - and so do the seeds: the bow amplitude is the circular-arc sagitta `L/2 * tan(|dtheta|/4)`, the exploratory seed's turn threshold comes from the robot's track width, and the initial `dt` is proportional to the segment length (PQ-B's Q2, which converges more slowly but found a better optimum on 18 of 32 missions). Every number measured before this change describes a different planner, so a measurement has to say which layout it was taken on.

- `pybricks_code/` is firmware code, not CPython (`pybricks.*`, `umath`); do not run it on the host. `complex_mission.py` is generated by `--export-format python`; regenerate, don't hand-edit - `sysid_digital_twin.py` imports it for its held-out replay, so it stays tracked (KI-018). Everything else that only served the hand-written demos - `complete_mission.py`, `mission_1..5`, `mission_template.py`, the old `sysid_data_logger.py` and the host-side `plot_tracking.py` - is in `pybricks_code/archive/`, which the mpy-cross compile test does not descend into. `robot.py` is the hub menu and routes the two supported programs: the pushed trajectory (`hub_runner.py`) and the SysId collector. `hub_runner.py` imports `ramsete_compact_events.py`, the packed-trajectory entry point; `ramsete_fast.py` is a thin wrapper over `ramsete.py`, so the list-of-dicts and reference paths run the same controller. The commands are in `pybricks_code/README.md`.

- The maintenance shape of the tree, and what is deliberately not done. **`overboard/paths.py` owns the repository's directories**: the root, the firmware, the examples, the missions, the fields, the mats, the calibration folder and the studio's own assets. Nothing else in the package climbs its own parents to find them - `tests/test_paths.py` reads the tree and fails if a module rebuilds a path by hand, so the answer stays in one place. The three entry points (`main.py`, `gui_server.py`, `diagnostics.py`) still spell the root out once each, because they have to run as a script before the package is importable. **`TrajectoryOptimizer._solve_once` is one long method** - variables, collocation, boundary conditions, the objective, the epigraph bounds and the IPOPT options, in that order - and splitting it into a builder per part was considered and **deferred**: the build is linear, the parts share a dozen locals, so the split would move the code rather than clarify it, and it would put the solver's numerics at risk for no behaviour change. The solver benchmark (`python benchmark.py --mode solver`) is the reference table for any change here. The iteration log is the one part that already lives outside the method, on the instance, and `solve` reads it after the call; it is not a thread-safety problem, because every parallel path builds its own optimizer per candidate and the one shared resource - the CasADi/MUMPS call - is already serialised by `CASADI_IPOPT_LOCK`. The seed provider is `overboard/core/frontier_seed.py`: the analytical seeds and the `generate_canonical_seeds` triad, with the dead branches removed and the output proven unchanged (KI-053).
